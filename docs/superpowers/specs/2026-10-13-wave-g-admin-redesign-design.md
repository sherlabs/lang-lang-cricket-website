## 0. Findings from reproducing the audit locally (before design)

Findings 1, 3, 4, 5 and 6 were confirmed in code or by running it. **Findings 2 and 7 are hypotheses**: the mechanism fits the code and the symptoms but was not reproduced end to end, and the 503s were never reproduced. WP-0 includes one acceptance step that turns hypothesis 2 into evidence (see WP-0 Tests, "characterisation test").

Local dev (`langlang_dev`, port 4500, a throwaway admin created with `seed:admin`), Chrome at 1440 wide. Screenshots (1440, current state): Home `/var/folders/fb/4n4m4y5526s8qtqg5q55sfb40000gn/T/claude-chrome-screenshots-A9ljd4/screenshot-1791896290833-0.jpg`, Social posts `.../screenshot-1791896290834-1.jpg`. 390px captures are taken per work package as "before" shots (section 9), because the spec only redesigns what it photographs.

Findings:

1. **A blank cream page while the server works.** The first load of `/admin` rendered an empty cream page (Payload's `RootLayout` background, nothing else) until the whole server render finished; the same happens on `/admin/login`. There is no `loading.tsx`, no `Suspense` around the page body, and the custom views `await` 4 to 8 queries before sending a byte (`SocialView`: settings, club, queue, heartbeat; `Dashboard`: club, notification centre, milestones, sync panel). `RootLayout` also awaits `getTheme()` (two database reads, fatal on Vercel production if they fail) before anything streams. How long this takes on a cold serverless instance with a remote database is **not measured** (the audit document records no timings; the owner's "10 to 20 seconds" is an impression, not a figure used here). WP-0 adds the timing log that will measure it.
2. **Hypothesis: `requireUser` turns a slow or failed session lookup into a login bounce, and it drops the query string.** `payload/components/AdminPage.tsx` `requireUser(view, path)` redirects to `/admin/login?redirect=<path>` whenever `isStaffUser(req.user)` is false. Payload resolves `req.user` through `executeAuthStrategies`, which catches any error from the session lookup (`findByID` with `useSessions: true`) and returns `user: null` after logging it. So, if a lookup errors (a timeout, an exhausted pool; `DATABASE_POOL_MAX` default 5, shared by every RSC render a page triggers), it would look exactly like "not signed in", the login page would then run its own successful lookup and redirect straight back, which matches the bounce the owner saw. This has **not** been reproduced; WP-0 proves or disproves it with a characterisation test (force the lookup to throw, show the old code redirects). The query-string loss is certain from the code, not a hypothesis: the redirect value is built from the fixed view path (`'/social'`), so deep links die in the bounce.
3. **A signed-in non-staff user loops.** A signed-in selector or disabled user who opens a custom view is redirected to the login page; Payload's `LoginView` redirects any signed-in user to `redirect`; the custom view redirects again. That is an endless redirect, not a message. The view must render "this is for the committee" instead of redirecting when someone is signed in.
4. **The Social composer loses its state even with a valid session (reproduced locally).** `view.searchParams` and `initPageResult.req.url` arrive empty at the view for a hard load of `/admin/social?type=sponsor-thanks&source=1,2&style=bold&size=landscape` (a debug log in the view printed no keys; the page function logged one render with `{}` and a second with the parameters). The composer's `useEffect` then calls `history.replaceState` to `/admin/social` with no query, erasing the deep link in the address bar. Two defects, both fixed in WP-0: the composer must not rewrite the address until it has read it, and it reads state on the client from `window.location.search` (the URL is the source of truth) instead of depending on server props that can arrive empty.
5. **First clicks do nothing** is the same cause as finding 1 seen from the other side: the page is server-rendered late and hydrates late, with the entire composer (and the queue below it) in one client bundle and no skeletons. Fix: shell first, skeletons for slow regions, small client islands.
6. **Sponsor logos are "undrawable" because of the format, not the data.** `sponsorChoices()` (`lib/social/sources/content.ts`) accepts a logo only if `isDrawableImageType` (PNG or JPEG, decided from the stored MIME label) and `loadImageDataUri` succeeds. Local sponsors 1 to 4 (the ones with logos) are `image/webp`, so they all fail; satori cannot draw WebP. Contributing causes: the fetch goes to the site URL over HTTP with `redirect: 'error'` and a short timeout (a protected preview answers with a redirect or 401), only `resolveServerURL()` and the Blob host are allowed, and a failed result is cached for the life of the process (`imageCache.set(key, null)`, and the Map is unbounded). Fix in WP-2b: read the stored file server side (no HTTP round trip to ourselves; exact calls in WP-2b), decide the format by sniffing bytes, convert WebP, GIF, AVIF to PNG with `sharp` (already a dependency), reject unsafe SVG, cache successes only in a bounded LRU, and tell the person which logo failed and why when one still cannot be used.
7. **Hypothesis, not verifiable from here:** the HEAD/RSC 503 responses under Vercel deployment protection. They are consistent with finding 2 (function errors or timeouts under load, then `user: null`) but are not reproduced, and could equally be the platform's protection layer. WP-0 therefore also adds the diagnostics that would show which it is: a server-timing log line per admin render (auth ms, theme ms, view ms), and a log that distinguishes "session lookup failed" from "no cookie" from "session expired". Acceptance does not depend on identifying the 503s: a session check that errors is retried once and, if it still errors, shows a calm "we could not check your sign-in, try again" page instead of a bounce.

## 1. Design direction (frontend-design pass)

**Tone: calm, warm, club-house, not dashboard-y.** The public site is bold (black, gold, condensed display type, DESIGN.md). The admin keeps the same brand but turns the volume down: paper-warm surfaces (`brand-stone` and `brand-cream`), white cards, ink text, the club gold used sparingly (primary action, active state, focus ring, the 4px gradient rule at the top of the sidebar, as on the public nav and footer). The display font appears only on page titles and the Home greeting. Body is the Inter stack already loaded. One idea carries the whole admin: **every page is a short sentence plus one obvious next step.**

Differentiator that makes it feel like this club's tool rather than Payload: a task-first sidebar with a crest header, grouped by what people do (group labels only, not extra entries; see WP-1), icons, and the current club's own colours. A phone gets a slide-over menu and, on the Social composer only, a bottom action bar, not a squeezed desktop sidebar.

### 1.1 Tokens (one admin stylesheet, one mapping)

All values come from the `theme` global through the `--brand-*` channel triples already placed on `<html>` by `app/(payload)/layout.tsx`. A single file, `payload/components/admin-theme.css`, maps them onto Payload's variables and defines the admin's own semantic tokens; nothing else in the admin stylesheet names a colour. (`admin.css` today has hex-free colours except `background:#fff` on the crest tile; that becomes `rgb(var(--brand-white-ish))`: a new `--admin-surface` token.)

| Token | Built from | Use |
| --- | --- | --- |
| `--admin-bg` | `--brand-stone` | page background |
| `--admin-surface` | white mixed from `--brand-cream` at 40 percent | cards |
| `--admin-ink` | `--brand-black` | headings, primary text |
| `--admin-text` | `--brand-charcoal` | body |
| `--admin-muted` | `--brand-grey`, clamped by `deriveAdminTokens()` (see Contrast below) | help text, meta |
| `--admin-line` | `--brand-black` at 10 percent | borders, dividers |
| `--admin-accent` | `--brand-gold` | primary button fill, active marker, focus ring |
| `--admin-accent-ink` | `--brand-gold-deep`, clamped by `deriveAdminTokens()` | gold text on light |
| `--admin-tint` | `--brand-gold-pale` | selected row, callout, active nav |
| `--admin-danger`, `--admin-danger-tint` | theme-independent red-700 / red-50 (as the public error box) | errors only |
| `--admin-ok`, `--admin-warn` | green-700 / amber-800 on their 50 tints (status pills; fixed, not brand, so state colour never depends on a club palette) |

Payload variable mapping (all in the same file): `--theme-bg`, `--theme-elevation-0..1000` (ramp from `--admin-surface` to `--admin-ink`), `--theme-success-*` (existing gold ramp, kept), `--theme-error-*`, `--font-body`, `--font-serif` (the display font for titles), `--style-radius-s/m/l` (6, 10, 16 px, from DESIGN.md radii), `--base` (spacing grid). Primary buttons are the accent fill with `--admin-on-accent` text.

**Contrast is computed, not asserted.** The ratios are not stated as facts here; they are requirements enforced by code:

- `lib/theme/admin-tokens.ts` (pure) exports `deriveAdminTokens(theme)`, which produces every derived admin token (`muted`, `accent-ink`, `tint`, `on-accent`, `line`, `focus`) from the club palette and applies the **fallback**: if a derived text token misses its ratio against its surface, it is clamped toward ink (`--admin-ink`) for text on light surfaces and toward white for text on the accent fill, stepping lightness until it passes (never failing silently; the clamp is logged once at theme save). The admin CSS reads the clamped values, so a club with a weak palette still gets a readable admin.
- Required pairs, all checked by `tests/admin-contrast.test.ts` against the **resolved seed theme and the neutral template theme**: `muted` on `surface` and on `bg` (>= 4.5:1), `ink` and `text` on `surface` and `bg` (>= 4.5:1), `accent-ink` on `tint` and on `surface` (>= 4.5:1), `on-accent` (ink or white, whichever passes, chosen by the helper) on the `accent` button fill (>= 4.5:1), status pill text on its tint (>= 4.5:1), the focus ring on both `surface` and `bg` (>= 3:1), control borders on `surface` (>= 3:1). The test fails the build if the seed theme does not meet them after derivation; a unit test also feeds deliberately bad palettes (pale grey, near-white gold) and asserts the clamp produces passing values.
- `ThemeContrast` (the theme editor widget) is extended to call `deriveAdminTokens()` and show the same pairs, so the editor warns about the derived admin tokens, not only the public-site pairs it checks today.

### 1.2 Type, spacing, shape, motion

- **Type scale (rem):** page title 1.75 to 2.25 (display font, clamp), section title 1.125 (600), body 1 (16px minimum on inputs, no iOS zoom), small 0.875, micro label 0.75 uppercase tracked only for the sidebar group labels. Line height 1.5 body, 1.2 titles. Help text 0.875 muted, one sentence, max 60 characters per line.
- **Spacing grid:** 4px base; 8, 12, 16, 24, 32, 48. Page gutter 16px on a phone, 32px from 1024. Card padding 16 (phone) and 24. Page max width 1200px; forms 760px; Social composer uses the full width.

- **Dark mode:** not in this wave (admin `theme: 'light'` stays); tokens are structured so it is a later token swap.

## 2. WP-0: P0 fixes (ship first, own commit set)

### Behaviour

1. **Never a blank screen.** Add `app/(payload)/admin/[[...segments]]/loading.tsx` rendering the shell skeleton (sidebar skeleton with the crest from the already-resolved theme CSS variables, page-header and card skeletons). It uses only CSS and the `--brand-*` variables set on `<html>` (no data). **A segment `loading.tsx` wraps only the page below `RootLayout`; it cannot cover work `RootLayout` awaits above it.** `RootLayout` currently awaits `getTheme()` (two database reads) and Payload's `RootPage` awaits init and the auth/permission lookup, so the layout's awaits must be made non-blocking for the skeleton to appear at all. Hence `getTheme()` becomes non-blocking for the admin:
   - **Cache semantics:** a per-instance in-process cache with stale-while-revalidate (a stale value older than 60 seconds is served while one refresh runs). **Invalidation:** the `theme` global's `afterChange` hook (and the `club` global's, for the crest/name) clears the cache in the same instance, so a colour change saved on an instance shows on that instance's next render, within a refresh. **Other serverless instances lag by up to a minute**; that is stated in `admin-design-system.mdx`, and the WP-1 acceptance step "changes the admin within a refresh" is verified on the instance that saved (dev: one instance).
   - **First-ever render with an empty cache and a slow or failed read:** the admin renders with the **seed theme** (`resolveTheme(null)` defaults) immediately and the real theme replaces it on the next render once the background read completes; the admin never waits on, or fails because of, the theme read. The public-site fatal rule is untouched.
   - **Expected floor:** even with this, Payload's `RootPage` awaits its own init (config, importMap, `initReq` including the session lookup) before it renders the segment, so the first byte of the *page* cannot arrive before that. The deliverable is: the `RootLayout` shell and the `loading.tsx` skeleton stream first, and the view's own queries never delay the header. The floor is measured by the timing log (item 6) and reported, not promised as a number.
   - **Verification is in the production build** (`next build` then `next start`, final step only), not `next dev`, which does not stream or prerender the same way.
   Login gets its own `beforeLogin` content so the page is meaningful immediately.
2. **Auth that cannot bounce falsely.** Replace `requireUser(view, path)` with `requireStaff(view, searchParams)`. It never inspects `req.user` truthiness alone; it classifies the session into one of: `staff`, `not-staff`, `signed-out`, `error`.
   - `req.user` staff: continue.
   - **Where the error signal comes from.** `executeAuthStrategies` and therefore `payload.auth` swallow lookup errors and return `user: null`, so neither can tell "threw" from "null". The wrapper `payload/admin/session-check.ts` (`checkSession(payload, headers)`) is used **only when `payload.auth` returned a null user and an auth cookie is present** (`<COOKIE_PREFIX>-token`, name from config). It verifies the JWT itself with the payload secret (expired or invalid token means `signed-out`, no database call), then calls `payload.findByID({ collection: 'users', id, depth: 0, overrideAccess: true })` **directly inside its own try/catch**, so a thrown error is an observable `error`, and checks the session id against the user's sessions. Outcomes: valid session and staff means continue (the first lookup failed transiently; this is the single retry), valid and not staff means `not-staff`, token invalid/expired or session absent means `signed-out`, the call throws or times out means `error`. (The JWT/session API names are confirmed against Payload 3.90.2 during implementation; if the session internals are not reachable the wrapper uses a second `payload.auth` call plus the logged `error` flag from a one-off `payload.logger` interceptor; the contract of the four outcomes does not change.)
   - **Retry bounds:** at most **one** extra attempt per render, only after a null result with a cookie present, never when there is no cookie, using the same `payload` instance and its existing pool (no new connection, no `Pool` constructor), with a **2 second timeout** (`Promise.race`; a timed-out query is still released by the pool, so one attempt cannot hold more than one connection). No loop, no backoff queue. A bare retry on every null would worsen the exhausted-pool case it targets; this one cannot.
   - `signed-out` (no user and no cookie, **or** the retry returned cleanly with null/expired): redirect to `/admin/login?redirect=<full path and query>` (builder below). People whose session simply expired see the login page, not a "could not check" page.
   - `error` (the retry actually threw or timed out): render `AuthTroubleNotice` ("We could not check that you are signed in. Reload, or sign in again." with a Reload button and a Sign in link carrying the redirect), HTTP 200, never a redirect. This notice appears **only** for a thrown/timed-out lookup.
   - `not-staff` (signed in selector, disabled): render `NoAccessNotice` ("This part of the admin is for the committee.") with **no redirect**, so no loop. It does not name the person's role or say why (they already know who they are); the "Go to the selector area" link is rendered **only** when the session's user really has the selector role, otherwise the only link is "Sign out".
   - **Redirect builder** (`lib/admin/redirect.ts`, pure): the target is built from `routes.admin` (config) plus the **known view path** (a constant per view) plus an **allowlisted re-serialisation of `searchParams`** (only keys the view declares, for example `type, source, style, size, text, tab, post` for Social; values re-encoded with `URLSearchParams`, each value capped at 500 characters, total capped at 2000). It does **not** read `x-url`, `next-url`, `Referer` or any client-influenceable header. The result is still passed through Payload's `getSafeRedirect` as a second gate. Tests: `//evil.test`, `/\evil.test`, `\\evil.test`, `javascript:alert(1)`, `%2F%2Fevil.test`, `/admin/../evil`, a value with CR/LF, an over-long query, and an unknown key (dropped) all produce either the safe admin path or the admin home.
3. **The login page is never blank and honours `redirect`.** `beforeLogin` renders a branded intro; the form is Payload's. A signed-in visitor to `/admin/login?redirect=...` goes to the redirect (Payload does this; test it with a query string and an encoded path). Unsafe redirects fall back to the admin home.
4. **Deep-link state survives, without a hydration mismatch.** Social composer (and every other custom view that has state in the URL: Selectors, Office filters, Fantasy tabs) treats the URL as the source of truth, but **never reads `window.location.search` during render**. The first paint (server and client hydrate) is a neutral state built from whatever server props arrived (possibly empty); the URL state is then applied in a `useEffect` after mount, behind the "disabled until hydrated" guard (item 5), so there is no hydration mismatch, flicker of live controls, or console error. The address is rewritten only after that initial read and only when the state differs. **Every URL value is validated before use** because it comes from a user-controlled URL and flows into API calls: `type` against `isGraphicType`, `style` against `isStyleKey`, `size` against `isSizeKey`, `source` ids against the picker's choices list (unknown ids dropped; at most 4 ids, each a positive integer or the known id format), `text` capped at 200 characters and stripped of control characters, `tab`/`post` against known values; anything invalid falls back to the neutral default. `text` in the URL is used only to fill the text box and is sent only to the caption and graphic endpoints; it is not logged (the timing log in item 6 records route names and durations, never query strings) and not sent to any analytics or third party. A unit test with an empty server prop and a populated address proves the composer selects the type and items after mount; another with hostile values proves the fallbacks.
5. **Fast interactivity.** Views render a header and skeleton immediately: slow data goes into `Suspense` regions (server components) so the shell, tabs and the first step are interactive while queue rows, previews and lists load; the composer's client bundle is split (dynamic import for the preview and scheduling panels); no view awaits more than one query before first paint. Interactive controls get `disabled` plus a skeleton until hydrated (`useHydrated`) instead of looking live and doing nothing.
6. **Diagnostics (logs only).** One structured log line per admin render in `AdminShell` (route name without query string, auth ms, theme ms, view ms, session outcome: `staff | not-staff | signed-out | retried-ok | error`). Nothing personal is logged. There is **no counter and no "System health" card** for retries: an in-process counter on serverless is per-instance and resets on cold start, so a "last 24 hours" figure would be false, and an honest one needs storage, which this wave does not add. The logs are the evidence.

### Data model, access, migrations, classification
None. No collection or global change, so no migration. No new endpoint; `AdminShell` reads the existing request. The `afterChange` cache invalidation hooks touch no schema.

### Tests
- **Characterisation test (turns hypothesis 2 into evidence), written first.** An int test (`tests/int/admin-auth-bounce.int.test.ts`) forces the session `findByID` to throw (a stubbed `payload.db`/`findByID` in the test only) with a valid cookie. Step 1, committed against the *old* `requireUser`: assert the view responds with a redirect to `/admin/login` (the bounce is real). Step 2, after the change: the same setup returns `AuthTroubleNotice` with HTTP 200 and no `Location`. If step 1 does not redirect, hypothesis 2 is wrong and the spec's finding is corrected in the PR.

### WP-2b: Graphics layout quality and sponsor-logo pipeline (`lib/social/render.tsx`, `fit.ts`, `density.ts`, `logo.ts`, `specs/*`)

- **Balanced compositions for 1 to 4 items.** Sponsor thank-you, lineup and leaders use a layout table keyed by item count and size: 1 item = hero logo centred at 55 percent of the content height; 2 = two equal cells in a row (landscape and square) or stacked (portrait), each at 40 percent; 3 = one over two (square), three across (landscape), stacked (portrait); 4 = 2x2. Logos are fitted with `contain` into a paper tile that is at least 60 percent of its cell; the whole group is vertically centred in the space under the headline.
- **No large empty areas, measured on real renders.** The metric is **rendered, not estimated**: the test renders each case through the real satori pipeline to PNG (`sharp`), takes the content box (below the headline, above the footer), and computes `unused = 1 - (bounding box of non-background pixels inside the content box) / (content box area)`, plus the largest empty vertical and horizontal gap as a share of the box. `fit.ts` keeps a cheap estimator `emptyShare(layout, size)` (used at layout time to choose the larger scale), and a calibration test asserts the estimator is within 5 percentage points of the pixel metric over a sample set (so the estimator cannot drift). **Thresholds are a table, not one number:** `tests/social-layout-thresholds.ts` has a maximum unused share per type x size for the types the owner flagged (sponsor-thanks, results, leaders); others are reported, not failed, in this wave. The first-draft "28 percent" is withdrawn: it was not derived from anything. Procedure: at the start of WP-2b run the matrix against the *current* renderer and record the measured unused shares as the "before" column (committed as a fixture); the target for each cell is the lower of 25 percent and 60 percent of its measured "before" value, rounded up to a whole percent, and the table records both columns and the rule so a reader can see how it was chosen. A cell whose target cannot be met without breaking another rule (a single-line headline in portrait) is listed with the reason, not silently raised.
- **Auto-fit text instead of ellipsis.** A `fitText(text, boxWidth, maxPx, minPx, lines)` helper picks the largest size that fits within 2 lines, then wraps to 2 lines, and only as a last resort at the minimum size truncates at a word with an ellipsis. The width model is `GLYPH=0.58` times size by default (a crude average), extended with per-font width tables for the bundled faces; **the tables are validated, not trusted**: a test renders a fixed sample set of strings in each bundled font with real satori, measures the rendered width in pixels, and fails if the table estimate is off by more than 5 percent (and prefers over-estimating, so text never overflows). The `ellipsis` styles in `render.tsx` are replaced for opposition names, sponsor names, row text and details. The objective "no ellipsis" check is: for the audited strings list (long opposition name, long sponsor name, long player name, long grade label; committed as a fixture) `fitText` returns `truncated: false` at size >= the type's `minPx`, and the real render of each contains no `...` glyph run (pixel check on the text region is not needed; the layout result's `truncated` flag is the objective output).
- **Public team names.** Graphics show the team's public name (the club name and the grade label from the name-and-grade-labels feature, `docs/features/name-and-grade-labels.mdx`), never the internal PlayHQ team name. One pure `publicTeamName(match)` in `lib/social/sources/shared.ts` used by results, toss, preview, lineup (tested with neutral fixture names; the audit's real examples live only in the audit doc). The club name comes from the club global (short name) and the internal-name detection from `PLAYHQ_TEAM_PREFIX`; the strings "Showing on the website" and "Senior Men" are never literals in code: they come from the grade/team labels and the `lib/admin/copy.ts` label map, with seed defaults only in the preset.
- **Sponsor logo fix** (`lib/social/logo.ts`, server only), `loadLogoDataUri(mediaDoc)`, with these exact steps:
  1. **Read the bytes** from the stored upload, with no HTTP request to ourselves: in development and test, `fs.readFile` of the file under the `media` collection's upload directory (path from the collection config `staticDir` + stored `filename`, resolved and checked to stay inside that directory); on Vercel (Blob storage), the stored `url` fetched server side from the Blob host only with `@vercel/blob`'s server SDK `head`/authenticated fetch using the existing server token (never a client token), `redirect: 'error'`, 5 second timeout, response size capped. Input bytes are capped at 5 MB before any decode (`too_large`).
  2. **Sniff the type from the bytes**, ignoring the stored MIME label: `sharp(buf).metadata()` format must be one of png, jpeg, webp, gif, avif, svg; anything else is `unsupported`. (This replaces the MIME-only `isDrawableImageType`, so a mislabelled file neither passes nor fails wrongly.)
  3. **Bound decoding**: `sharp(buf, { limitInputPixels: 25_000_000, animated: false, failOn: 'error' })` (stops decompression bombs from WebP/AVIF/GIF; first frame only), resize so the long edge is at most 1024, then to PNG, trim transparent padding.
  4. **SVG** is the risky case (librsvg can follow `xlink:href`/`href` to local files in some builds). Rule: reject, with `unsupported`, any SVG whose text (decoded as UTF-8, case-insensitive) contains `<image`, `<use` with an `href`/`xlink:href` that is not a same-document fragment (`#id`), `<!ENTITY`, `<!DOCTYPE` with an internal subset, `<script`, `<foreignObject`, or any `href`/`url(` reference that is not a same-document fragment; otherwise rasterise at 2x with the same pixel limit. Rejection is preferred over sanitising (no sanitiser dependency). Tests include each rejected construct.
  5. Returns `{dataUri, width, height}` or `{error: 'unsupported' | 'missing' | 'too_large' | 'unreadable'}`.
  6. **Cache:** key `id + updatedAt`, successes only, in a bounded LRU (at most 64 entries and 16 MB of data URIs, evicting least recently used); failures are cached for at most 60 seconds. The old unbounded process-lifetime Map is removed.
  `sponsorChoices()` returns `logo: 'ok' | 'none' | 'failed'` and no longer uses MIME-only validation.
