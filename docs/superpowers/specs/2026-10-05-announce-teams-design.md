## 0. Findings that shape the design

1. **`isStaff` means "any logged-in user" today.** `payload/access/index.ts` defines `isStaff = Boolean(req.user)`, and `staffOr`, `isStaffField` do the same. The same assumption is spread across the codebase (full list and the guard in 3.2): `payload/collections/News.ts` (line 28), `Yearbooks.ts`, `SavedReports.ts`, `payload/endpoints/mergePlayers.ts` (`!req.user`), `payload/hooks/storyLifecycle.ts` (`submittedByAdmin`), `AdminPage.tsx`, the dashboard, `PlayerDataToolsView`, `lib/payload/staff-route.ts` (`requireStaff`, used by `app/api/admin/playhq-refresh`, `app/api/admin/players-sync` and `statlab/saved/route.ts`) and `lib/preview-queries.ts` (`Boolean(user)` decides draft preview). The moment a third role exists, every one of those would grant a selector full committee rights (hidden players, unpublished news, merge players, draft preview, PlayHQ refresh). Payload's built-in collections (`payload-preferences`, `payload-locked-documents`, `payload-jobs`) also default to "any logged-in user". **First task of WP-A is to make "staff" mean `admin | editor` and not disabled**, and to prove it with a matrix test (section 3.9). This is the highest-risk part of the whole feature.
2. **Payload 3.90.2 cookie name is global.** `generatePayloadCookie` uses `config.cookiePrefix` (`payload-token`), not the collection. A separate `selectors` auth collection would fight over one cookie in the same browser. So selectors are rows in `users` with `role: 'selector'`.
3. **There is no email adapter** (forgot-password is disabled for that reason). Invitations therefore cannot be emailed; they are a copyable link the committee shares by message (section 3.4).
4. **PlayHQ players carry no phone number.** The "last 4 digits of the phone" PIN of #15 needs a private contact store that does not exist (section 4.2).
5. **Upcoming fixtures are not stored.** `matches` holds only FINAL games. Upcoming games come from the PlayHQ live cache (`lib/playhq/queries.ts`, `getClubGames`, TTL 30 min). Availability and team sheets need a durable fixture key, so a small snapshot collection is added (section 4.3).
6. **GraphQL is disabled** (`graphQL: { disable: true }`), so "REST + GraphQL" access below is REST and the Local API only. Public pages use `lib/*-queries.ts`, which state their own visibility filter because the Local API ignores access rules.
7. **Payload 3.90.2 session internals** (verified in `node_modules/payload/dist`). `getFieldsToSign`, `jwtSign` and `resetLoginAttempts` are exported from the main `payload` entry. **`addSessionToUser` and `generatePayloadCookie` are exported only from `payload/shared`** (`dist/exports/shared.js`), not from `payload`, so the helper imports them from there. `jwtSign` takes `{ fieldsToSign, secret, tokenExpiration }` (seconds) and returns `{ exp, token }`; `getFieldsToSign` takes `{ collectionConfig, email, sid?, user }`. `useSessions` is on by default, so a JWT is valid only while its `sid` is in `user.sessions`, **but `addSessionToUser` returns `sid: undefined` if sessions are switched off**, so the config pins `auth.useSessions: true` explicitly and the spike asserts it. `addSessionToUser` stamps the session `expiresAt` from the collection `tokenExpiration`, so session lifetime is a collection setting (see 3.6). That gives us both a way to mint a session without a password (3.5.1) and a way to revoke one (clear `sessions`).
8. **Facebook (checked against Meta's manual-flow doc, current Graph version shown as v25.0).** Dialog `https://www.facebook.com/<ver>/dialog/oauth` (client_id, redirect_uri, state, response_type=code, scope), token `GET https://graph.facebook.com/<ver>/oauth/access_token` (client_id, redirect_uri, client_secret, code). PKCE is **not documented** for this flow, so **v1 does not send it**: the defence is `state` bound to a cookie-only nonce, a `__Host-` cookie in production and single use (3.5). If Meta documents PKCE later it is a small follow-up. The data-deletion callback is mandatory for a Live app. Facebook does not guarantee that `email` is confirmed, so **the spec never uses the Facebook email for any decision** (3.5).

## 1. Rules for the whole spec

**Commits and safety.** Conventional commits, explicit paths, no push, last line `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`. All DB work is local (127.0.0.1:54329; `langlang_dev`, `langlang_test`, `langlang_mig`). No live PlayHQ calls (run anything that could reach PlayHQ with `PLAYHQ_CLIENT_ID=` empty; tests use fixtures/mocks). No real Facebook calls: the OAuth endpoints are an injectable `fetch` in tests. Dev server ports 3900-3999.

**Migrations.** One migration per WP (`pnpm payload migrate:create wp_a_selectors`, `wp_b_availability`, `wp_c_selection`), schema-qualified, `.ts` and `.json` committed; `pnpm generate`, then `git add payload-types.ts "app/(payload)/admin/importMap.js"`; `pnpm check:migrations` and `pnpm check:generated` pass.

**Admin classification.** Every new collection and global gets `admin.group: false`, plain labels and helper text. New third class: **selection collections** (`selectionCollections` in `payload/admin/navigation.ts`): `admin.hidden: true` for every role, managed in the selector area, not editable as raw rows in the admin. Their REST write access is **admin or editor only** (section 2); selector writes go through server actions (5.4 and 2). `tests/admin-visibility.test.ts` is extended to classify them (hidden, anonymous denied) the way it does `internalCollections`. Two real admin entries are added: **Selectors** (an Advanced custom view, section 3.4) and **Selection settings** (advanced global). **The everyday cap stays at 16 and nothing is added to the everyday menu**: creating logins is an occasional task. The committee reaches it through a dashboard `jobTiles` entry "Add a selector" (deep link to the Selectors view) and the Advanced entry. Editors cannot see Advanced (`hiddenFromEditors`), so the Selectors entry is declared with `hiddenFromEditors: false` (**verify** `navigation.ts` allows a per-item override; if it does not, the Selectors view becomes a tab inside the existing "Committee & contacts" page instead, which editors already see). The matching test asserts the everyday cap is still 16, records the reason ("selectors are an occasional task, reached by tile and Advanced") and asserts editors can reach the Selectors view.

**Personal data.** Phones, PINs, emails, Facebook ids and invite tokens are never public over REST or the Local API as used by pages. **`hidden: true` is not protection on its own**: it only strips values from output, and Payload's `validateQueryPaths` does not stop REST `where=` filtering on a hidden field (a read-capable user could binary-search a value). So every sensitive field uses field-level `access.read` (and `create`/`update`) set explicitly: `facebookId`, `inviteTokenHash`, `inviteExpiresAt`, `pinHash`, `pinSalt` are `read: nobody` (code reads them with the Local API and an explicit `select`); `phone` is `read: isSelection`, `update: isSelection` (in `player-selection-profiles`, which itself is not REST-readable by editors beyond that rule); `email` on `users` is readable by admin, and by an editor only on selector rows through the collection read filter. `hidden: true` is kept as well so the admin form does not render them. A REST `where` probe test (3.9, 4.9) filters on each of these fields as every non-admin role and expects a 400/403 or an empty result indistinguishable from "no match", never a distinguishing count.

**Hidden-player reads.** Selector reads of `players` through REST follow anonymous rules (hidden players disappear). The builder, the warnings ("selected player hidden") and publish validation therefore read `players` through the Local API with an explicit filter and `overrideAccess: false` plus the selector `user` where access allows, or through `lib/selector-queries.ts`, a single file that states its filter for each query (including hidden players, which selectors may see inside `/selector` only).

**Mobile first.** Every `/selector` page is designed at 360 px first: single column, 44 px tap targets, sticky bottom action bar, no hover-only controls, no horizontal page scroll (matrix scrolls inside its own container with a sticky name column).

**Docs.** Feature docs (`selector-accounts`, `availability-link`, `squad-boards`, `team-selection-and-announce`, `match-day-overview`) plus the index; `tests/feature-docs.test.ts` enforces shape. Docs are written when each WP lands, describing only what is built. The docs must also state the honest limits: last-4-digit phone PINs are guessable by teammates and shared within families; withdrawing a team cannot recall an image Facebook has already scraped; Facebook sign-in can fail inside the Messenger, Facebook or WhatsApp in-app browser.

**Scope cuts and deferrals (review outcome, see Appendix D).** v1 does not include: `@dnd-kit` (Up/Down plus a Move sheet is the only reordering/moving UI), form-trend scoring (only the raw last-5 string), Autofill and Copy last week's side, the sponsor strip and the `?format=feed` image, availability ranges and overrides (per-fixture answers only), the Contacts CSV import, PKCE and the `FACEBOOK_PKCE` and `FACEBOOK_REDIRECT_ORIGIN` settings, and the `qrcode` dependency (link plus Copy only). Each is a candidate follow-up issue under #38.

**Club-neutral config.** Everything club or country specific comes from config: sign-off line (`club.teamsSignOff`, default empty), matchday label (`site-settings.matchdayLabel`, default "Matchday"), the Meta app name (`club` short name, shown in the doc as `<club name>`), `CLUB_COUNTRY` / `CLUB_LOCALE` (phone parsing and the privacy notice template), `CLUB_TIMEZONE`, `COOKIE_PREFIX`. The guard scope (`tests/no-brand-hex.test.ts` and the club-name guard) is extended explicitly to the new paths: `app/(frontend)/selector/**`, `app/(frontend)/teams/**`, `app/(frontend)/availability/**`, `lib/selector-*.ts`, `lib/facebook-login.ts`, `lib/oauth-cookie.ts`, `lib/throttle.ts`, `lib/selection/**`, `lib/teams-queries.ts`, `lib/availability-*.ts`, `payload/endpoints/selectors.ts`, `payload/components/SelectorsView.tsx`. Example opponents such as "Nar Nar Goon" appear only in this spec and test fixtures.

## 2. Roles and permissions model (the contract)

Role values on `users.role`: `admin`, `editor`, `selector`. Helpers in `payload/access/index.ts` (all treat `disabled` users as nobody). Every other module asks these helpers; none asks "is there a user".

| Helper | True for |
| --- | --- |
| `isAdmin` | admin |
| `isStaff` | admin, editor |
| `isSelection` | admin, editor, selector |
| `selectionOr(where)` | selection users see all, others see `where` (rarely used; most selection data has no public read) |
| `staffOr(where)` (existing) | now staff only (was any user) |

The JWT carries `role` (already `saveToJWT`). A custom Payload `access.admin` on `users` returns true only for admin and editor, so a selector who signs in cannot open `/admin` (Payload shows its unauthorised view) and cannot pass any `isStaff` check. Because the minted `payload-token` is the same cookie that opens `/admin`, **only `role = selector` accounts may use Facebook sign-in** (3.5); admins and editors keep password login, so a Facebook match can never become a passwordless admin session.

Per-resource access (REST and Local API with `overrideAccess: false`; anonymous is denied everywhere unless stated). **Selection collections are not REST-writable by selectors.** Raw REST writes would bypass the pure validators (a selector could write `slots` with arbitrary `guestName` or `size`, or forge `source: 'player'` and `setBy`). Selector writes go only through server actions and endpoints (`app/(frontend)/selector/actions.ts`) that validate with the pure functions and **re-derive `setBy`, `source` and `updatedBy` from `req.user`**, never from input. Every Next server action is a public POST, so **each action calls `requireSelection()` itself** and uses the Local API with `overrideAccess: false, user`. A guard test (3.9) bans `overrideAccess: true` under `app/(frontend)/selector/**`; the only privileged writes live in `lib/selector-queries.ts`, which re-checks the role and is the one reviewed place. Where a write truly needs to bypass collection access (publish fields, throttle rows), the function takes the already-verified user and says so in a comment.

| Resource | read | create | update | delete |
| --- | --- | --- | --- | --- |
| `users` | admin all; editor: self + role selector; selector: self | admin any; editor only role selector (forced, 3.3) | admin any; editor: self (no role) + selectors; selector: self (name, password only) | admin; editor only selectors |
| `player-selection-profiles` (WP-B) | admin, editor; selector via `lib/selector-queries.ts` | admin, editor | admin, editor (`pinHash`, `pinSalt` never writable over REST); selectors via actions | admin, editor |
| `selection-fixtures` | admin, editor; selector via queries | nobody (code) | nobody (code) | nobody |
| `availability` | admin, editor; selector via queries | admin, editor | admin, editor | admin, editor |
| `squads`, `squad-members` | admin, editor; selector via queries | admin, editor | admin, editor | admin, editor |
| `team-sheets` | admin, editor; selector via queries | admin, editor | admin, editor (publish fields only through the publish action) | admin, editor |
| `throttle-hits` (internal) | admin | nobody | nobody | nobody |
| `selection-settings` global | selection | n/a | admin (link rotation and enable switch go through an action that calls `requireSelection()`) | n/a |
| `announcements` (existing) | public published | staff | staff; `link` validated as a relative path or `https:` URL only (a `validate` function rejecting `javascript:`, `data:` and protocol-relative values, tested) | staff; the publish action writes with the Local API after its own role check |
| `payload-preferences`, `payload-locked-documents`, `payload-jobs` (built-ins) | own rows only (access explicitly overridden, not the "any user" default) | own | own | own; jobs admin only |

Public pages never read these through REST. `/teams` and `/availability/[token]` read through `lib/teams-queries.ts` and `lib/availability-public.ts`, each stating its filter. Selector pages read through `lib/selector-queries.ts` (Local API with explicit filters; see section 1).

## 3. WP-A: Selector accounts and Facebook sign-in (#39)

### 3.1 Schema (migration `wp_a_selectors`)

New `users` fields. Access is explicit per field (see section 1: `hidden` alone is not protection); `admin.condition` admin-only so the raw user form stays simple:

- `role` gains option `selector` (label "Selector (picks the teams)").
- `disabled` checkbox (default false), index. Not hidden (shown on the Selectors view). Changing it triggers the session-clearing hook in 3.3.
- `inviteTokenHash` text (SHA-256 hex of a 32-byte random token; the token is high-entropy so a plain SHA-256 is enough), **indexed** (`index: true`), `inviteExpiresAt` date, `invitedAt` date. `access.read` nobody. The invite token is the **only** authority to claim a login for the first time (3.4, 3.5).
- `facebookId` text with a normal **unique index** (`unique: true`; Postgres allows many NULLs in a unique index, so no partial index is needed and a hand-written partial index would drift from `check:migrations`), `facebookLinkedAt` date. `access.read` nobody. Only ever set on `role = selector` rows (3.5, enforced by a `beforeChange` hook and tested).
- `lastLoginAt` date, `lastLoginMethod` select (`password`, `facebook`).

Derived status (pure `lib/selector-status.ts`): `disabled`, else `invited` (no login yet and invite window open), else `invite expired` (no login yet, window closed), else `active`. "Facebook linked" is a separate chip.

### 3.2 Making "staff" mean staff (first commit)

1. Rewrite the helpers in section 2 and update **every** caller: `payload/collections/News.ts`, `Yearbooks.ts`, `SavedReports.ts`, `payload/endpoints/mergePlayers.ts` (`!req.user`), `payload/hooks/storyLifecycle.ts`, `AdminPage.tsx`, `Dashboard`, `adminOnly.ts`, `PlayerDataToolsView`, `lib/payload/staff-route.ts` (`requireStaff`, used by `app/api/admin/playhq-refresh`, `app/api/admin/players-sync`, `statlab/saved/route.ts`) and `lib/preview-queries.ts` (`getPreviewUser`). `requireStaff` and `getPreviewUser` call the shared `isStaff` logic from `payload/access` instead of `Boolean(user)`. Also override the built-in collections' default access (`payload-preferences`, `payload-locked-documents`, `payload-jobs`) to own-rows only.
   **Grep guard test** (`tests/staff-guard.test.ts`): fails on `Boolean(req.user)`, `!req.user`, `Boolean(user)` and `req.user ?` truthiness checks outside `payload/access/**`, so a new caller cannot reintroduce the bug.
2. `Users.access.admin` returns `role in (admin, editor) && !disabled`.
3. Collection `beforeLogin` hook throws the same `AuthenticationError` for a disabled user (uniform message, no hint that the account exists).
4. Matrix test (3.9) is written before the other WP-A code and must pass at the end of this commit. It covers every app collection **and** `payload-preferences`, `payload-locked-documents` and `payload-jobs`.

### 3.3 Creating selectors: privilege rules

- `users.access.create`: admin any; editor allowed, but a `beforeValidate` hook **forces** `role = 'selector'` for an editor (the default is `editor`, so omitting `role` must not create an editor), strips `disabled`, `facebookId`, `sessions`, `lockUntil`, `loginAttempts`, `_verified`, `inviteTokenHash`, `inviteExpiresAt` from editor input, and rejects any other role value with 403 instead of silently coercing (so an escalation attempt is visible in tests).
- `users.access.update`: editor may update self and any `role: selector` row. The `role` field keeps `access.update: isAdminField`, so an editor can never change anyone's role (including their own or a selector's), and a hook rejects a body that tries (403, not silent drop).
- An editor cannot read, update, unlock or delete admins or other editors (`where role = selector`).
- A selector updates only self, only `name` and `password` (field access; hook rejects `email`, `role`, `disabled`, `facebookId`). **Password rules apply on every path** (REST, endpoint, admin form, `payload.update`): a `beforeValidate` hook rejects a password shorter than 10 characters, and a selector changing their own password through REST must also send `currentPassword`, verified with the same comparison as login (the committee "Set a password" endpoint is the only way to set one without it).
- **Session revocation is a collection hook, not endpoint behaviour.** A `beforeChange` hook clears `sessions` (all, or all except the current one when the user changes their own password) on: a password change, a `role` change, an `email` change, and `disabled` going true. An admin ticking `disabled` in the raw user form therefore revokes cookies too. Test: disable via the raw form (`payload.update` with `disabled: true`), then `payload.auth` with the old cookie fails.
- Changing a selector's email clears `facebookId`, clears sessions and requires a fresh invite (a new `inviteTokenHash` and window). A different email is a different person until proven otherwise; the email is **never** compared against Facebook, so this rule only prevents a stale link surviving.
- Disabling sets `disabled` and (by the hook above) clears `sessions`. It keeps the Facebook link so re-enabling restores access; unlinking is a separate button.
- Deleting an editor-created selector is allowed for editors; deleting any non-selector is admin-only.

### 3.4 The "Add a selector" flow and invitations (admin custom view)

Custom admin view `payload/components/SelectorsView.tsx` at `/selectors`: an **Advanced** nav entry "Selectors" visible to admin and editor (section 1), plus a dashboard `jobTiles` entry "Add a selector". Same pattern as `ApprovalsView`. Plain English, large buttons:

1. List: name, email, status chip (Invited, Active, Disabled), "Facebook linked" chip, last sign-in.
2. **Add a selector**: two fields, name and email (the email is only the login name for the password path and a label; it is not used to bind Facebook). Creates the user with a random 32-byte password nobody knows (Payload requires one), `inviteTokenHash`, `inviteExpiresAt = now + 14 days` (setting `SELECTOR_INVITE_DAYS`, default 14). The result shows the invite link once with **Copy link** and **Share** (`sms:`/`https://wa.me/?text=` links built client-side; no third-party call) and the sentence "Send this to <name>. It opens the selector tools and lets them sign in with Facebook or choose a password. It works for 14 days and once."
3. Per row actions: **New invite link** (replaces the token and reopens the window; it is also what "Allow Facebook sign-in again" does: it **mints a fresh invite link**, there is no email-based window), **Unlink Facebook**, **Disable / Enable**, **Set a password** (typed by committee, min 10 chars, for people with no Facebook and no patience), **Remove**.
4. Endpoints in `payload/endpoints/selectors.ts` (`POST /api/selectors/create|invite|unlink|disable|enable|set-password|remove`), each guarded by `refuseNonStaff` (admin or editor, 401/403), each calling the Local API with `overrideAccess: false, user: req.user` so the collection rules of 3.3 are the single source of truth, and each unit-tested for refusal by selector and anonymous.

The invite page `/selector/invite/[token]` (public, noindex, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`): looks up by `sha256(token)` in constant time against the single indexed row, checks the window, shows "Hi <first name>" and two choices: **Continue with Facebook** (when configured; this starts the flow carrying the invite token in the signed cookie, 3.5) or **Choose a password** (min 10 chars; then signs in). Wrong or expired token: one generic page ("This link has expired. Ask the committee for a new one."). Throttled per IP as a soft signal (section 4.4).

**Consuming the invite is atomic and closes the window on every path.** A single statement `UPDATE users SET invite_token_hash = NULL, invite_expires_at = NULL WHERE invite_token_hash = $h AND invite_expires_at > now() RETURNING id` (through `payload.db.drizzle`, schema-qualified, covered by `check:migrations` because the columns come from the migration) is the only way the token is spent, so two requests racing on one link cannot both succeed: the loser gets zero rows and the generic page. The same consume runs on a successful password choice and on a successful Facebook bind (3.5 step 4b); the token and `inviteExpiresAt` are therefore cleared together on any successful first sign-in. After that the account is not bindable by anything except a new invite or the authenticated Link flow (4c). Test: two concurrent consumes (`Promise.all`), one wins; a consumed token is dead on both paths.

### 3.5 Facebook sign-in (invite-only OAuth 2.0 authorisation code flow)

Config (`lib/facebook-login.ts`, reads env at call time, no module-scope secrets):

| Env | Meaning |
| --- | --- |
| `FACEBOOK_APP_ID`, `FACEBOOK_APP_SECRET` | The club's Meta app. **Either unset: no button, every `/selector/facebook/*` route returns 404**, the login page shows only the password form. |
| `FACEBOOK_GRAPH_VERSION` | Default `v25.0` (**verify** when setting up; versions are retired about two years after release). One constant in `config/site.ts`. |

Redirect URI = `${origin}/selector/facebook/callback`, where `origin` is `resolveServerURL()` (production: `NEXT_PUBLIC_SERVER_URL`; preview: `https://${VERCEL_BRANCH_URL}`, the stable per-branch alias). There is no override setting. Meta requires every URI to be registered exactly, so **only production and one stable preview alias support Facebook sign-in**; any other host shows the password form only (the page checks `host === origin host`).

**Flow**

1. `GET /selector/facebook/start?next=/selector/teams&invite=<token>` (or `&link=1` for the authenticated link). Generates `state` (32 random bytes, base64url) and a separate `nonce` (32 random bytes) that lives **only in the cookie**; `state` sent to Facebook is `HMAC(key, nonce)` truncated, so the cookie nonce and the returned state must correspond. No PKCE parameters are sent (finding 8). Stores `{ nonce, state, next, invite?, userId?, iat }` in one cookie. Cookie attributes: httpOnly, `SameSite=Lax` (must be sent on the top-level GET back from Facebook), `Max-Age=600`, and in production the **`__Host-` prefix** (`__Host-${COOKIE_PREFIX}_sel_oauth`), which forces `Secure`, `Path=/` and no `Domain`, so a sibling subdomain cannot plant or overwrite it. **This is incompatible with `Path=/selector/facebook` scoping, so the cookie is `Path=/` and the HMAC (key derived from `PAYLOAD_SECRET` by HKDF, label `selector-oauth`) is for integrity only.** The rationale is corrected: a signed cookie does **not** stop cookie tossing, because an attacker can call `/start` themselves and obtain a validly signed cookie, finish the Facebook login to get a code, then plant the cookie in the victim's browser from a sibling subdomain (login CSRF). The `__Host-` prefix is what stops the planting; in local development over http the prefix is dropped and the cookie is `Secure`-less (documented). `next` is validated by `safe-next`: **normalise first** (percent-decode once, reject if decoding changes the value again), then require exactly `/selector` or `/selector/` followed by path characters, reject `//`, `\`, `%2f`, `%5c`, any control character (including `%00` to `%1f`) and any scheme; otherwise fall back to `/selector`. Redirects to the dialog with `scope=public_profile`, `response_type=code`. The scope is `public_profile` only: email is no longer requested because it is never used.
2. `GET /selector/facebook/callback?code&state` (or `error`): response headers `Cache-Control: no-store`, `Referrer-Policy: no-referrer`. Steps in order, each failing to the same friendly page with a specific internal log line: cookie present and signature valid, not older than 10 minutes; `state` equals the value derived from the cookie nonce (`timingSafeEqual`); **the cookie is cleared immediately (single use, also on every failure)**; **if the cookie carries an `invite`, it is re-validated now** (exists, unexpired, unconsumed), not trusted from `/start`; `error` param (user pressed Cancel) shows "Facebook sign-in was cancelled".
3. Server-to-server token exchange (`fetch`, 5 s timeout, `client_secret` only here, never to the browser, never logged) then `GET /me?fields=id,name`. The access token goes in the `Authorization: Bearer` header **(verify Graph accepts it on `/me`; if not, fall back to the `access_token` query parameter and redact it from all logs and error reports)**. The access token is used once and discarded; **we store only the Facebook user id**. (`debug_token` is not needed because the token came straight from our own exchange.)
4. Account resolution, in this order (**never creates a user, never compares any Facebook email, and only ever matches `role = selector` rows**):
   a. A user with `facebookId = me.id` and `role = selector` exists: if `disabled`, fail with the generic "can't sign in" page; else sign in (first-time sign-in is not involved, so there is no invite to consume). A `facebookId` on a non-selector row is never honoured: that row is refused and logged, and a hook prevents it being set.
   b. Else, if the (re-validated) cookie `invite` token resolves to an enabled `selector` row with no `facebookId`, **consume the invite atomically (3.4)** and bind: set `facebookId`, `facebookLinkedAt`, in the same transaction. The authority is possession of a valid, unexpired, single-use invite token and nothing else. There is **no email-based binding and no "open window by email"**: a Facebook account that merely carries a selector's email gets nothing, whether the window is open, was open earlier, or the email was changed since.
   c. Else, if the cookie carries `userId` (the **authenticated link** flow below) and that user is a signed-in enabled selector, bind to that user.
   d. Else fail with one generic page for every non-match reason (no account, invite expired or already used, already bound to another id, staff account): "That Facebook account is not linked to a selector login. Ask the committee for a new invite link, or sign in with your password and link Facebook from My account."
5. Mint the session (3.5.1), set the cookie, redirect to `next`.

**Authenticated link flow.** A signed-in selector opens `/selector/account` and presses **Link Facebook**; `/selector/facebook/start?link=1` puts their `userId` in the cookie and the callback additionally checks that the current `payload-token` still belongs to that user; step 4c binds. This is the safest binding because it trusts nothing about Facebook's profile. **Unlink** is available there and in the admin view.

**Login fixation and CSRF protections** (each has a test): state derived from a cookie-only nonce, compared in constant time, single use; `__Host-` cookie in production, short-lived; the invite re-checked at callback; the session is always newly created (`addSessionToUser` gives a new `sid`; any prior `payload-token` is overwritten, never reused); the callback never trusts query parameters other than `code` and `state`; strict `next` allowlist; no auto-creation; selector-role-only binding and sign-in; a Facebook id can bind to one user only (unique index); an already-bound user cannot be re-bound; per-IP throttle on `/start` and `/callback` as a soft signal (section 4.4).

**Data deletion and deauthorise callbacks** (mandatory for a Live app): `POST /selector/facebook/data-deletion` and `/selector/facebook/deauthorize` accept `signed_request`, verify `HMAC-SHA256(app_secret, payload)` in constant time and reject others with 400, then clear `facebookId` for `user_id` (the committee's account stays; only the link goes) and return `{ url: <origin>/selector/facebook/deletion-status?code=<random>, confirmation_code: <random> }`. The status page is static ("The Facebook link has been removed"). **These routes are exempt from the throttle, from cookies and from session checks** (Meta calls them server to server, with no cookie, from shared addresses). Documented as the URL to paste into the Meta console.

#### 3.5.1 Minting a normal session without a password (investigated, verified by a spike test before building on it)

Payload's custom `auth.strategies` only **authenticate an incoming request**; they do not create sessions or cookies, so a strategy alone cannot sign someone in after an OAuth redirect. The cleanest supported mechanism in 3.90.2 uses exported primitives, exactly what `login` does after the password check. **Import paths matter**: `getFieldsToSign`, `jwtSign`, `resetLoginAttempts` come from `payload`; `addSessionToUser` and `generatePayloadCookie` come from `payload/shared` only.

1. `const doc = await payload.db.findOne({ collection: 'users', where: { id: { equals: id } } })` (the raw row, as `login` does; `addSessionToUser` writes the whole object back).
2. `import { addSessionToUser, generatePayloadCookie } from 'payload/shared'`; `const { sid } = await addSessionToUser({ collectionConfig, payload, req, user: doc })`. **Throw if `sid` is undefined** (sessions off would silently mint a cookie that never expires server-side).
3. `const fields = getFieldsToSign({ collectionConfig, email: doc.email, sid, user: doc })` then `const { token } = await jwtSign({ fieldsToSign: fields, secret: payload.secret, tokenExpiration: collectionConfig.auth.tokenExpiration })` (argument shape confirmed on 3.90.2: `{ fieldsToSign, secret, tokenExpiration }`, returns `{ exp, token }`).
4. `generatePayloadCookie({ collectionAuthConfig, cookiePrefix: payload.config.cookiePrefix, token })` into the redirect response.
5. Update `lastLoginAt`, `lastLoginMethod`, call `resetLoginAttempts`.

The result is the same `payload-token` cookie `payload.auth()`, `/api/users/me` and the access functions already understand; logout, `sessions` revocation and `tokenExpiration` (7 days) behave unchanged. **Spike test first** (`tests/int/selector-session.int.test.ts`): it imports from exactly the paths above (so a moved export fails the test, covering the import path); asserts `collectionConfig.auth.useSessions === true` and that `sid` is defined; mints for a seeded selector, calls `payload.auth({ headers })` with that cookie and asserts `user.role === 'selector'`; asserts that clearing `sessions` makes the same cookie fail; asserts `/admin` access is denied; and asserts a staff row is refused by the mint helper's caller (3.5 step 4). The helper lives in one file (`lib/selector-session.ts`) with a header comment pinning the Payload version, and the test fails loudly on a Payload upgrade that changes it. A custom `auth.strategies` entry is **not** needed. If the spike fails, the fallback is `payload.login` with a per-login random one-time password written to the user, rejected because it would invalidate the password fallback on every Facebook sign-in.

## 4. WP-B: Availability and squads (#15 #16)

### 4.1 Overview

Players answer in / maybe / out per fixture from one club link with a PIN, no account. Selectors see a players-by-fixtures matrix and set answers for people (phone calls). Squad boards hold who is in each grade squad.

### 4.2 Where private contact data lives

New collection `player-selection-profiles` (selection class, hidden in admin), one row per player (`player` unique relationship):

- `phone` text, normalised to digits (national format validated by a pure `normalisePhone()` using `CLUB_LOCALE`/country config; never logged; **readable and writable by selection users only**, never by anonymous, never on any public query).
- `phone` text, normalised to digits by a pure `normalisePhone()` that takes the country from `CLUB_COUNTRY` / `CLUB_LOCALE` config (a small per-country table; default is a permissive digits-only normaliser; never logged). Field access `read`/`update`: selection users only (via actions), never anonymous, never on any public query.
- `pinHash` text and `pinSalt`, both `access.read` nobody and not writable over REST, `pinSource` (`phone` | `manual`), `pinSetAt`.

How data gets in: selectors type a phone on the player card (`/selector/players/[slug]`) or the matrix "add phone" (server action). A bulk Contacts CSV import is **deferred** (follow-up issue). Phones are not added to `players`, `player-seasons` or any export (`statlab` CSV, history export): a test greps the export column sets.

PIN design: default PIN is the last 4 digits of the phone (the issue's rule); selectors can set a manual PIN (4 to 6 digits) for players with no phone and tell the player. Storage: `scrypt` (Node `crypto`, no new dependency) over `pepper + pin` where the pepper is HKDF-derived (label `selector-pepper`), per-row salt, constant-time compare. **scrypt parameters are chosen to keep a request affordable on serverless** (for example N=2^14, r=8, p=1, about 30 to 60 ms), because verification runs once per candidate player on every attempt; the candidate set is capped (reject a name matching more than 5 players). Honest limits, stated in the doc: a 4-digit PIN has 10,000 values; **last-4 phone PINs are guessable by teammates and shared within families** (anyone who knows a number knows the PIN); the pepper protects a stolen database without the secret, and the throttles below only slow an online attacker. Clubs worried about this should use manual 6-digit PINs. PINs are never shown after setting except once to the selector who set a manual one.

### 4.3 Fixtures source and what is stored

New selection collection `selection-fixtures`, one row per PlayHQ game of the club's senior teams: `gameId` (unique), `gradeId`, `gradeName`, `clubTeamId`, `clubTeamName`, `roundName`, `localDate`, `localTime`, `startsAt`, `venueName`, `venueSuburb`, `opponentName`, `isHome`, `status` (`upcoming`, `final`, `removed`), `syncedAt`.

Why stored: availability and sheets need a stable key that survives a PlayHQ outage or a cache expiry, public `/teams` must not call PlayHQ per request, and a rescheduled game must keep its responses. Refresh: `refreshSelectionFixtures()` in `lib/selection-fixtures.ts` reads `getClubGames` for the current season (the same cached path `/fixtures` uses), upserts by `gameId` (never deletes: a game that disappears from PlayHQ becomes `removed`, its availability and sheet stay and the sheet shows "This game has been removed or moved on PlayHQ"), and keeps only games from 14 days ago to 120 days ahead. Triggers: appended to the existing nightly `players-sync` cron, and a **Refresh fixtures** button in the selector area (throttled 1 per 5 minutes per user through `throttle-hits`). Tests use the existing PlayHQ fixtures; scripts run with `PLAYHQ_CLIENT_ID=`. Juniors are excluded using `isJuniorGrade`.

### 4.4 Brute-force protection that works on serverless

No in-memory counters (every invocation may be a fresh instance). `lib/throttle.ts` over an internal collection `throttle-hits` (`key` unique hashed string, `count`, `windowStart`, `lockedUntil`, `strikes`), written with one atomic SQL statement through `payload.db.drizzle` (`INSERT INTO payload.throttle_hits … ON CONFLICT (key) DO UPDATE …`, **schema-qualified inside the `payload` schema**; the table comes from the WP-B migration so `check:migrations` covers it and a test replays the statement against the migrated schema) so concurrent requests cannot both read the old count. API: `hit(key, { limit, windowMs, lockMs })` returns `{ allowed, retryAfter }`; `fail(key, …)`/`clear(key)` for credential keys. Backoff: after `limit` failures lock for `lockMs`, doubling per further strike **up to a cap of about 1 hour** (a 24 h lock keyed on a claimed name would let anyone lock a named player out for a day).

**Client IP is a soft signal.** `lib/client-ip.ts` trusts only `x-vercel-forwarded-for` (or `x-real-ip`) and **only when `process.env.VERCEL` is set**; otherwise there is **no IP key at all** (the first `x-forwarded-for` hop is attacker-controlled off Vercel and would bypass the cap or poison a victim's bucket, so it is never used). Mobile carriers share addresses (CGNAT), so IP caps are generous and never the only control, and an IP limit alone never produces a hard lockout of a remembered device or of a selector with a valid session.

Keys (all hashed with an HKDF-derived key, label `throttle-key`, so the table holds no names or IPs):
- `avail:link:<linkVersion>:<bucket>`: **per link and per claimed name**, 5 failures then 15 min lock, doubling to the 1 h cap. Applied to every attempt including names that do not exist, so unknown and known names behave identically. **Unknown names do not each get a row**: a name that matches no player is hashed into one of 64 buckets (`hash(name) mod 64`), so random names cannot grow `throttle-hits` without bound; known names get their own key. (The bucket sharing means a flood of unknown names can lock out other unknown names, which has no cost.)
- `avail:ip:<ip>`: soft, only when a trusted IP exists: 60 attempts per 10 minutes.
- `avail:link:<linkVersion>:all`: 300 failed attempts per hour on a link trips a **global pause** of 15 minutes **for new identification only** (a name and PIN attempt); **remembered devices (a valid `_avail` cookie) are never affected**, and writes a notice for the selector overview ("Someone is guessing PINs on the availability link. Consider rotating it.").
- `sel-login:ip:<ip>`, `sel-oauth:ip:<ip>`, `sel-invite:ip:<ip>`: 60 per 10 minutes each when a trusted IP exists; none otherwise. The Facebook data-deletion and deauthorise routes are exempt.
- **Bypasses for the legitimate**: a valid remembered-device cookie bypasses the per-name and global locks (it was earned with a correct PIN), and a selector can issue a **one-time code** for a named player (shown once, stored hashed, single use, expires in 24 h) that identifies them without the PIN and without being blocked by a lock another person caused.
Nightly cleanup deletes rows idle for 2 days (added to the cron). Lock responses are uniform: "Too many tries. Please try again later or ask a selector." with no indication of which key tripped.

### 4.5 The no-login availability link and the identification flow

`/availability/[token]` (public, `noindex`, disallowed in robots). The bearer token is in the URL, so every response from this route sets `Cache-Control: no-store` and **`Referrer-Policy: no-referrer`** (the token must not leak through Referer to anything the page links to or loads). The token is a **secret deterministic value**: `base64url(HMAC-SHA256(hkdf('avail-link'), 'v' + linkVersion))`, 43 characters. It is never stored, so a database leak does not reveal it; the server can always re-display it to selectors; **rotate = increment `selection-settings.linkVersion`**, which instantly invalidates the old link, every remembered device and every lock key. Compared with `timingSafeEqual`; wrong token returns a plain 404 page (no hint). `selection-settings.linkEnabled` switches the link off (404 for all).

Identification, chosen for safety and usability: **no list of players is ever shown or returned before authentication.** The page asks **name** (free text, "as on PlayHQ") and **PIN**. The server normalises the name (`normaliseName`, same key as `player-aliases`), looks up players on the current roster (members of any current squad, plus any player with a profile), derives candidates (capped, 4.4), and verifies the PIN against each candidate with a dummy hash when there is none (equal timing). Wrong name, wrong PIN, no PIN set, ambiguous (two players share name and PIN) and locked all return the same message ("We could not match those details."), plus the lock message only when throttled. Ambiguity creates a notice for selectors ("PIN clash between two players called <name>", resolved by setting a manual PIN). On success the server sets a signed httpOnly cookie `${COOKIE_PREFIX}_avail` (`{ playerId, linkVersion, iat }`, 90 days, HMAC with the `avail-cookie` HKDF key, SameSite=Lax; `__Host-` prefixed in production) so the next visit needs no PIN and is not subject to the name or global locks; "Not you? Switch" clears it. One identity per device (families re-identify), simple and safe.

After identification the player sees **only their own** answers and the club's upcoming fixtures for their squad grade(s) (public information already on `/fixtures`): three big buttons per fixture (**In**, **Maybe**, **Out**) and an optional 140-character note (plain text, stored escaped-on-render). They cannot see other players, the squad, selections or anyone's phone. Changes are accepted until a configurable cutoff (`availabilityLockHours`, default 0 = always) after which the page says "Selection has started; call a selector". Responses are written by a server action that re-reads the cookie and recomputes everything from the player id in the signed cookie, never from form fields.

## 5. WP-C: Selection and announce (#17, lineup of #21, overview of #20)

### 5.1 Team sheet data

Selection collection `team-sheets`, one per fixture (`fixture` unique): `slots` (array of `{ player (rel, optional), guestName (text, optional), order (1-based), isCaptain, isKeeper }`, exactly one of `player` or `guestName`; **`guestName` is validated by the pure validator: 2 to 40 characters, letters, spaces, apostrophes and hyphens, no digits, no `@`, no phone-like sequences**), `size` (`11`, `12`, `13`, `0` for open; default from `selection-settings.defaultXiSize`), `markedReady` (checkbox), `notes` (private), `revision` (int, increments on every save), `updatedBy` (derived server-side), `publishedSnapshot` (json, hidden: `{ revision, publishedAt, size, slots: [{ playerId | guestName, order, isCaptain, isKeeper }] }`), `publishedAt`, `publishedBy`, `publishCount`, `announcementId`. Selectors cannot REST-write the sheet at all (section 2); the save action runs the validators and the publish fields are written only by the publish action with the Local API after a role check. The builder warns that a typed guest name is **published to the public page**.

**Concurrency**: saves carry `expectedRevision`; a `beforeChange` hook rejects a stale save with 409 "Someone else changed this team. Reload to see their changes." Nothing silently overwrites another selector.

Derived status per sheet (pure `lib/team-status.ts`): **Not started** (no slots), **In progress** (some slots, not marked ready or short of `size`), **Ready** (marked ready, slots meet size, a captain, a keeper, no blocking warning), **Needs attention** (any warning below). Published is a separate chip ("Published", "Published, changes not published").

### 5.2 Balance, warnings and form (pure, `lib/selection/`)

Roles per player: stored `role` if set, else suggested from data (keeper if `canKeep` or any `keeperCatches/stumpings` in `match-fielding`; bowler if `bowlBalls` ≥ 120 in the last two seasons of `player-seasons` and batting average low; batter if `bowlBalls` < 30; all-rounder when both; else "unknown"). Counts: batters, bowlers (bowler + all-rounder), keepers, unknown. Warnings (plain text, never blocking publish except where noted): no keeper (`keeper` tag missing), no captain, fewer than 5 bowling options, fewer than 5 batters, an unknown-role player count above 3 ("roles missing, balance is a guess"), a selected player marked **out** (or in a range) for that fixture (**strong**), selected in another grade's XI the same day, selected player hidden or removed, fewer slots than `size`, game removed or rescheduled since last save. Warnings recompute on every render from the same functions the server uses at publish time.

**Form read** (deliberately minimal in v1): the player card and the Add players sheet show only the **raw last-5 string** from stored `match-batting`/`match-bowling` rows (`match-appearances.player`, `matches.status = final`, newest first, within 400 days; fill-in rows with no player link excluded), e.g. "23, 4, 51*, 0, 12" and "2/31, 0/22, …". Players with no stored rows show **No data**, never zero. **Hot, steady and cold trend scoring is deferred** (it needs a baseline and minimums that are easy to get wrong; a follow-up issue). The doc states the stored match window (rows exist only from the PlayHQ backfill window) and that form is a prompt for the selector, not a verdict. Sources are read-only existing queries (`lib/match-store`), cached under the existing `MATCH_STORE_TAG`.

### 5.4 Announce: the Publish action

Server action `publishTeams({ gameIds, announce })` in `app/(frontend)/selector/actions.ts`: **calls `requireSelection()` itself** (server actions are public POSTs) and uses `overrideAccess: false, user` except for the publish-field write inside `lib/selector-queries.ts` after the role check; re-validates each sheet with the same pure functions (blocks only on: no slots, slot count above a fixed `size`, a player who is hidden or missing, an invalid `guestName`; everything else is a warning shown on the confirm dialog with a "Publish anyway" tick), then for each sheet in a transaction writes `publishedSnapshot`, `publishedAt`, `publishedBy`, `publishCount + 1`. The confirm dialog repeats that guest names and the whole XI become public.
1. **Public teams page.** `/teams` (the weekend's published XIs per grade) and `/teams/[gameId]` (one game). Reads only `publishedSnapshot` (so edits stay private until **Publish changes**), resolves names at render with the visibility filter (`hidden = false`), uses `displayName` exactly as player pages do, links names to `/players/[slug]`. A hidden player in a published snapshot is shown as "Player name withheld" in their slot so batting positions stay honest. Batting order is **public by default** (numbered); `selection-settings.publishBattingOrder = false` shows the XI alphabetically without numbers (captain and keeper tags stay). Draft, unpublished, withdrawn and unknown game ids all return **the same 404** from both the page and the image route (no way to tell them apart). Draft sheets are never selected, never in REST (no public REST at all) and never in the sitemap. `Cache-Control` s-maxage 300 plus tag `teams`. **Hiding a player or withdrawing a sheet revalidates the `teams` tag and the image routes immediately**: an `afterChange` hook on `players` (when `hidden` changes) and the withdraw action call `revalidatePaths`/`revalidateTag` for `/teams`, `/teams/<id>` and the lineup image paths, not only the publish action.
2. **Site announcement (optional, default on via `announceOnPublish`).** Upserts one announcement per weekend keyed by a hidden `autoKey` (`teams:<weekend start date>`): title `<matchday label> <date>` (label from `site-settings.matchdayLabel`, for example "Matchday 12 October"; never hard-coded copy), body a plain list (grade, opponent, time, a one-line XI), published = true. Adds an optional `link` field (relative path or `https:` URL, validated, 3.1/section 2) and `linkLabel` to `announcements` (migration `wp_c_selection`; the banner shows a button when set; **verify** `components/announcement-banner.tsx` copes) pointing at `/teams`. Existing announcements and the banner dismissal cookie (`${COOKIE_PREFIX}_ann_dismissed` stores the numeric id) are unaffected; a re-announce keeps the same id, so someone who dismissed it does not see it again, and the title gains "(updated)" only when the XI changed, which is acceptable and noted in Risks.
3. **Share material.** `generateMetadata` on `/teams` and `/teams/[gameId]` sets title, description (the plain-text lineup, truncated) and `openGraph.images` / `twitter.images` to the lineup image. **Lineup image route** `/teams/[gameId]/lineup-image` (public only for published sheets, the same 404 as the page otherwise, so Facebook's crawler can fetch it): `themedImageResponse()` from `lib/theme/og.tsx` (resolves the theme, loads the bundled fonts and the crest chain), `fontFamily 'Display'/'Body'`, colours from `ctx.theme.colors` only. One size, `1200x630`; shows crest, club short name, "Round 5 v <opponent>", date, venue and the numbered XI with C and WK badges. **The sponsor strip and the second `?format=feed` size are deferred.** Long names are truncated by width. **`Cache-Control` is set explicitly** on the image route (`public, s-maxage=300, stale-while-revalidate=600`, with the `teams` tag revalidating it). The doc states that Facebook caches the OG image for a long time and **withdrawing a team cannot recall an image Facebook or anyone else has already scraped**; the confirm dialog says so. Draft preview for selectors: `/selector/teams/[gameId]/preview-image` (auth-gated, `no-store`, draft allowed). **Download** button uses `?download=1` (`Content-Disposition: attachment; filename="<EXPORT_FILENAME_PREFIX>-<grade>-<date>.png"`). Route added to `outputFileTracingIncludes` in `next.config.ts` (fonts and crest) as the W1 pattern requires. **Copy post text**: pure `lineupText(sheet, fixture, club)` returns, for example, "B Grade v <opponent>, Sat 12 Oct, 1:00pm, <venue>\n1. A Smith (c)\n2. …\n8. J Jones (wk)\n<club.teamsSignOff if set> <site URL>/teams" with club name, sign-off line and URL from config; prefixed "UPDATED: " on a re-publish; a client Copy button using `navigator.clipboard` with a visible text area fallback.
4. **Sitemap, robots, cache.** `/teams` added to the static sitemap list (priority 0.5); `/teams/[gameId]` for published, non-removed fixtures of the last 60 days; `robots.ts` keeps `/selector` and `/availability/` disallowed and allows `/teams/*/lineup-image` explicitly (like `/api/public/players/`). Publishing calls `revalidatePaths(['/', '/teams', '/teams/<id>', '/announcements', '/sitemap.xml'], …, ['teams'])`.
5. **Changing a published sheet.** The selector sees a **Published, changes not published** chip and a diff (in, out, order moved, tag changed). **Publish changes** (re-announce) writes a new snapshot, sets `publishCount > 1`, the public page shows "Updated <time>" and the lineup image a small "UPDATED" tag; the announcement is updated in place with "(updated)" and a one-line change list in the body; the post text is prefixed. **Withdraw** clears the snapshot (page and image 404, caches revalidated as in 1) and unpublishes the announcement if no other sheet that weekend is published.

## Appendix A. Decisions worth challenging

1. Selectors live in `users` (shared cookie) rather than a separate collection; the cost is the helper rewrite of section 3.2, the gain is one login, one lockout and one cookie.
2. Facebook binding authority is **only** a valid, unexpired, single-use invite token (re-checked at callback) or the authenticated Link flow. Email is never compared, and only `role = selector` can use Facebook at all. A stricter club can disable Facebook entirely (unset the env).
3. The availability link token is derived, not stored, so it can be shown again without a secret column. Rotation is a version bump.
4. Name plus PIN instead of picking from a list. It costs a little typing and removes the roster-enumeration oracle.
5. Phones are visible to every selector. Convenient for chasing no-replies, but a wider audience than "committee only"; a club can restrict to editors by flipping one access function (documented).
6. Public teams page shows the batting order by default; a setting hides it.
7. The everyday admin cap stays at 16: Selectors is an Advanced entry plus a dashboard tile (section 1).
8. No email invitations (no adapter). If an email adapter is added later, the invite link can be sent from the same endpoint (new issue under #38 when created).

## Appendix C. Risks

- **Privilege escalation through the role change** is the main danger: mitigated by the helper rewrite, 403-not-silent-drop on forbidden fields, the matrix test and the review gate that nothing else uses `Boolean(req.user)`.
- **PIN strength.** Four digits is weak by nature; the pepper, per-player and per-link lockouts, the global pause and rotation are the real controls, and the docs say so. Clubs worried about this can use manual 6-digit PINs.
- **Facebook app review and Live mode** are outside our control; the password path means the feature never blocks on Meta. Facebook binding needs a short-lived, single-use invite link, visible in the admin.
- **Phone numbers** are personal information (privacy law varies by country; for example the Australian Privacy Act, and under-18s with a parent's number): collected for selection only, never public, never exported, removable per player. The docs carry a one-paragraph notice **template** (with the country/law named from `CLUB_COUNTRY` config, not hard-coded) the club can show at registration.
- **Announcement re-use** after a dismissal means a re-published team does not re-show the banner to someone who dismissed it. Accepted; the `/teams` page always shows "Updated".
- **Image route cost.** Satori rendering is CDN-cached with explicit headers and tag revalidation; no remote logos in v1.
- **Serverless write races** on selection data: single-row memberships, revision checks and atomic throttle upserts are used instead of array writes.
- **Fixture drift** between PlayHQ and the stored snapshot: refreshed nightly and on demand, `removed` instead of delete, warning on affected sheets.
