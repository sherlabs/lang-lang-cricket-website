## 0. Findings that shape the design

Checked against this branch on 2026-10-13.

1. **Facebook sign-in already exists and must be reused, not copied.** `lib/selector-oauth.ts` holds `handleStart`, `handleCallback`, `resolveAccount` (a: already linked, b: invite, c: authenticated link flow) and `handleDataCallback`. `lib/oauth-cookie.ts` signs the single-use `{nonce, next, invite?, userId?, iat}` cookie (HKDF label `selector-oauth`, `__Host-` prefix in production, 10 minutes) and `stateFor(nonce)` is a 43 character base64url value. `lib/facebook-login.ts` is env-gated by `FACEBOOK_APP_ID`/`FACEBOOK_APP_SECRET`. `users.facebookId` is hidden, unique, write-guarded by `facebookIdRules` (only the OAuth flow, via `context.facebookBind`, may set it, and only on a selector row). The broker flow adds a second way to obtain a verified `facebookId`; everything after that (invite-only binding, `mintSelectorSession`) is shared.
2. **Broker protocol (v1), from `websport-common-auth/docs/protocol.md` and `src/`.** Start: `GET BROKER/v1/facebook/start?club=&return_to=&nonce=&state=`. `nonce` is 16 to 128 characters of `A-Za-z0-9_-`; `state` is 1 to 256 characters of `A-Za-z0-9._~-`. `return_to` must be an absolute URL whose origin is in the club's `origins` and whose path equals the club's `returnPath` exactly (no query, fragment, credentials or encoded slashes). The broker answers 303 to `SITE<returnPath>?websport_assertion=<JWT>&state=` or `?websport_error=<denied|facebook_error|invalid_response|exchange_failed>&state=`. The assertion is an EdDSA JWT (`kid` in the header) with `iss` (broker origin), `aud` (site origin), `sub` (app-scoped Facebook id), `name` (untrusted), `club`, `nonce`, `amr:["facebook"]`, `iat`, `exp = iat + 60`, `jti`. JWKS is `BROKER/.well-known/jwks.json` (OKP/Ed25519 keys, cached 5 minutes). Events are `POST <origin><eventsPath>` with `{ "event": "<JWT>" }`; claims `iss, aud, type (facebook.data_deletion | facebook.deauthorize), sub, iat, exp = iat + 300, jti` and no `club` or `nonce`. Health is `GET /healthz` returning `{ ok, facebookConfigured, clubs, keys }`. The broker's `CLUBS` entry for this site is `{ id, name, origins, returnPath: "/selector/facebook/broker-callback", eventsPath: "/api/websport-auth/events" }`.
3. **App-scoped ids differ per Meta app.** A Facebook id obtained through the shared broker app is not the id the same person has in a club's own app. Switching mode therefore breaks existing links for people bound under the other mode. The design records which mode bound each id (`users.facebookIdVia`), routes events only to broker-bound rows, and documents that people re-link from My account after a switch. Password sign-in is never affected.
4. **`jose` is only a transitive dependency** (5.10.0 under Payload). WP-1 adds it as a direct dependency pinned to that exact version so the lockfile resolution does not change. `createRemoteJWKSet` cannot take an injected `fetch`, so the site keeps its own small JWKS cache and verifies with `createLocalJWKSet`; that also makes tests use a fake JWKS without network.
5. **Availability-link identification is player based, fantasy is member based.** `identify()` in `lib/availability-public.ts` matches a typed name against the current squads and checks a PIN stored on `player-selection-profiles`. Fantasy must also work for parents and supporters, who are not players and have no profile. WP-2 therefore reuses the primitives (derived link token and version, signed remembered-device cookie, scrypt PIN hashing in `lib/selection/pin.ts`, the atomic `hit`/`isLocked`/`clear` throttle in `lib/throttle.ts`, the per-name bucket idea in `lib/availability-throttle.ts`) but not the roster lookup; a fantasy manager chooses a team name and a PIN when joining.
6. **The match store already has what scoring needs, with honest nulls.** `deriveFacts` (`lib/stats/match/facts.ts`) yields a `FactSet` of club-side, visible-player facts for FINAL matches: `BatFact {status, runs, balls|null, fours|null, sixes|null, dismissal}`, `BowlFact {balls, maidens, runs, wickets}`, `CreditFact {catches, keeperCatches|null, runOuts|null, stumpings|null}`, `Appearance`. `getSeasonFacts(seasonStartYear)` is the cached public path (hidden players already excluded). `readStoredBundles` is staff-only and must not feed a public page.
7. **Rounds already have a natural key.** `lib/selection/weekend.ts` groups club-local dates into Monday to Sunday weekends keyed by the Saturday. `selection-fixtures` carries `gameId`, `localDate`, `startsAt`, `roundName`, `status` and is refreshed nightly by the players-sync cron. `matches.gameId` is the same key, so a round's games and their stored results join on `gameId`.
8. **GraphQL is disabled** (`graphQL.disable`, pinned by a test). Access tables below therefore cover REST and the Local API. The Local API ignores access unless `overrideAccess: false`, so every query states its own visibility filter.
9. **Club identity is baked into the database schema.** `payload/globals/Club.ts` uses `defaultValue: d.<field>` from `payload/seed/club-defaults.ts` (the Lang Lang preset). Those defaults are compiled into the migrations as column `DEFAULT 'Lang Lang Cricket Club'`, `DEFAULT 'Caldermeade, Victoria'` and so on (seen in `20261003_023132_wp2_content.ts` and four later ones), and `getClub()` merges the saved row over the same module. A blank database migrated for another club therefore carries Lang Lang copy until every field is saved. WP-3 fixes this at the source.
10. **Club words still in code or shipped files.** Comments and the allowed set (`config/site.ts`, seeds, scripts, migrations) are already guarded by `tests/no-brand-hex.test.ts`. Remaining: the `CCCA Directory` document category (a Postgres enum value) and the `ccca` honours keyword in `lib/site-settings-core.ts`; `MELBOURNE`/`melbourneIso` identifiers in `lib/structured-data.ts` (names only, the value is `CLUB_TIMEZONE`); `public/googlef3f9083034ceae06.html` (a Search Console token file); static artwork (`app/favicon.ico`, `public/apple-touch-icon.png`, `public/og-image.jpg`, `public/assets/branding/{hero,logo}`, `public/assets/{documents,gallery,sponsors}`); README and DESIGN.md prose. `tests/branding-files.test.ts` already blocks another club's host from shipping Lang Lang's identical icon files.
11. **The committee menu has room but should not grow.** `everydayNav` is 15 of a cap of 16; `advancedNav` has no cap but is long. This wave adds **no everyday entry and no global**. Sign-in mode is an admin-only field group on the existing `site-settings` global (entry `site-settings` already exists, `hiddenFromEditors`; its `read` is `anyone`, so every new field there carries its own field-level access, see 3.2 and 4.2). Fantasy adds exactly one Advanced entry, the `/fantasy` management view (`forEditors`; a custom view is exempt from the global-slug rule). `tests/admin-visibility.test.ts` needs no new global slug.
12. **Leak audit today only warns.** `tests/int/isolate.ts` (`INT_LEAKS=1`) prints `[int:leaks] <file> left rows: ...` while processing the next file. `yearbook-ai.int.test.ts` leaves `users`, `users_sessions` and `yearbooks` (it logs in through `tokenFor`, which creates users, and its last test leaves a yearbook).

## 1. Rules for the whole spec

- Staff means admin or editor only. Selectors are a separate role and are never staff. A selector must be denied exactly like an anonymous visitor on every staff-only route and REST read.
- Anything club specific comes from the `club`/`theme` globals or env. No hex literal, no club name, no region or association word in app, component, lib or admin code. All fantasy and sign-in copy that names the club uses `getClub()`; labels such as the competition name are settings with neutral defaults ("Fantasy cricket").
- Personal or financial data is never public over REST or the Local API. Every query that serves a public page states its own filter.
- Every new collection or global is classified (`payload/admin/navigation.ts`, `tests/admin-visibility.test.ts`), has `admin.group: false`, plain labels and helper text, and a schema-qualified migration whose `.ts` and `.json` are committed. `payload-types.ts` and the admin import map are regenerated and `git add`ed before `pnpm check:generated`.
- Every external service is behind an env gate and a seam that tests replace: Facebook/Meta (only the broker is ever called, and only by the admin "Test connection" and the sign-in redirect), email, AI, social networks, PlayHQ. Tests set `PLAYHQ_CLIENT_ID=` and mock `fetch`. Nothing in this wave makes a live call from a test or from `seed:demo`.
- Mobile first (360px), keyboard and screen-reader usable, forms with real labels, no colour-only meaning, 44px tap targets.
- CSV exports are admin only and formula-injection safe (reuse `lib/stats/csv.ts`; a cell starting with `= + - @ tab CR` is prefixed with `'`).
- Dev servers use ports 4400-4499 only. Local Postgres only (`127.0.0.1:54329`); check `.env.local` hosts before any DB work; never read the main checkout's env, never set a Blob token, never run the Vercel CLI.
- Commits: conventional, explicit paths (`git add <paths>`, never `-A`), last line `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`. Never push.
- Iterate with `pnpm tsc --noEmit`, `pnpm generate`, single `pnpm vitest run tests/<file>` runs and eslint on changed files. One full vitest run and one `next build` at the end only. Never two vitest runs at once.

## 2. WP-0: leftovers

### 2.1 Trends chart label collision

**Cause.** In `components/stats/trend-chart.tsx` each bar value label is drawn at `ty = barTop - 4` and the last line point's label at `dotY - 8`. For "Average team total by season" the last bar is 149 and the last "against" point is 150; both sit within a pixel of each other, so the two labels print on top of each other. The same can happen at any x where a bar top and a line point are close, and for the last dot label against any bar label to its left.

**Fix.** Put label placement in the pure geometry (`lib/insights/chart.ts`) so it can be tested, and keep the component as markup.
- `buildTrend` produces a flat `labels: { id, x, y, text, anchor, kind: 'bar' | 'dot' }[]` list instead of `tx/ty` on bars and a hard-coded last-dot label. Each candidate gets a box (`w = text.length * CHAR_W + 4`, `h = 12`).
- Candidates are placed in priority order (dot label first, then bars left to right). Each tries positions in turn: above the mark, below the mark (a bar label may go inside the top of its bar in dark text on the accent fill, **only when `lib/theme/contrast.ts` says that text on the accent fill meets the label contrast requirement**; the caller computes `insideOk` once from the theme and passes it in, so the geometry stays pure; a dot label goes below the dot), then a second step further out. The first position whose box does not intersect any placed box and stays inside the plot area wins.
- If no position is free the label is dropped, never overlapped. The value is still in the "Show as table" element and in the `desc` takeaway text, so nothing is lost for any reader.
- `BarIn` and `TrendInput` keep their shape; the callers (`trends/page.tsx` and the player trends pages) do not change.

**Tests.** `tests/insights-pure.test.ts` gains: bars `[149]` with line `[150]` yields no two intersecting label boxes; a randomised property test over 200 generated series (n 1 to 12, nulls included) drawn from a **seeded PRNG** (a small `mulberry32(seed)` in the test with a fixed seed constant, so CI is deterministic; on failure the assertion message prints the series index) asserts pairwise no intersection, all boxes inside the viewBox, no NaN; a dropped label never removes a bar or a dot; with `insideOk = false` (an accent fill that fails the contrast check, built from a low-contrast fixture colour) no label is ever placed inside a bar, and with a passing accent it may be; the previous geometry assertions (empty and single-point series, nulls are gaps) still pass. A render test mirrors `win-loss-chart-render.test.ts`: the SVG text for the 149/150 case contains both numbers at different `y`.

**Docs.** One sentence in `docs/features/insights-trends-and-team-analysis.mdx` ("values that would overlap are moved or left to the table").

### 2.2 `yearbook-ai.int.test.ts` residue and a strict leak audit

- Add `dropTestUsers(payload, emails)` and a shared `cleanTestTables(payload, tables)` to `tests/int/helpers.ts` **from the start** (decided up front; there is no "more than ten files" escape hatch). `dropTestUsers` is a single drizzle transaction: it resolves the user ids, then deletes from every table that has a foreign key to `payload.users` (discovered once from `pg_constraint`, so `notifications`, `yearbooks.created_by`, `users_sessions`, `payload_locked_documents` and any later table are covered without a hand-kept list) and finally the users; it asserts afterwards that no row references those ids. ## 3. WP-1: Facebook sign-in through the shared broker (#40)

### 3.1 Behaviour

- **Mode** (admin-only field `signIn.mode` on `site-settings`, see 3.2): `off` (password only, every Facebook route is a 404), `broker` (default; the shared WebSport broker) or `own-app` (the existing direct flow from #39 with `FACEBOOK_APP_ID`/`FACEBOOK_APP_SECRET`).
- **Effective mode** is computed by `resolveSignIn(payload, env)` in `lib/signin/mode.ts`. Rules in order: (1) stored `off` is `off`. (2) stored `own-app` is `own-app` when both Facebook vars are set, otherwise `off` with a reason. (3) stored `broker` is `broker` when `AUTH_BROKER_ORIGIN` and `AUTH_BROKER_CLUB_ID` are valid; **when they are not and the own-app env is complete, it resolves to `own-app` with the reason "using the club's own Facebook app because the shared broker is not set up"**, so a deployment that already runs the #39 flow keeps its button across the migration (the default `broker` would otherwise silently switch Facebook off); when neither env is complete it is `off` with a reason. (4) Any non-`off` result is downgraded to `off` when the request host is not the configured site host (`hostSupportsFacebook`, the broker allowlists exact origins). Result: `{ kind: 'off' | 'broker' | 'own-app', reason?: string }`. Every existing and new route calls it; the login page and the invite page show the Facebook button only when `kind !== 'off'`. Env is read at call time, never at module scope. The cutover checklist also gets an explicit line: "Facebook sign-in: confirm the effective mode on Sign-in settings after deploy".
- **Start** stays one entry point, `/selector/facebook/start?next=&invite=&link=1`. In `own-app` mode it behaves as today. In `broker` mode it runs the same checks (IP throttle bucket `sel-oauth`, invite re-validation, authenticated `link=1` flow), creates the same signed cookie (`nonce`, `next`, `invite?`, `userId?`), then redirects to `BROKER/v1/facebook/start` with `club=AUTH_BROKER_CLUB_ID`, `return_to=<serverURL>/selector/facebook/broker-callback`, `nonce` (the cookie nonce, 43 characters of base64url, inside the broker's pattern) and `state=stateFor(nonce)` (43 characters, inside the pattern). The cookie is `SameSite=Lax`, which the browser sends on the broker's top-level 303 back.
- **Callback** `/selector/facebook/broker-callback` (GET only, 404 unless effective mode is `broker`): throttle; read the cookie (missing, tampered, older than 10 minutes: fail); constant-time compare `state` with `stateFor(cookie.nonce)`; clear the cookie on every path; if `websport_error` is present map `denied` to `cancelled` and anything else to `failed`; otherwise verify the assertion (3.3), consume the `jti` (assertions only), then call the **shared** `finishFacebookSignIn` (invite-only binding) and `mintSelectorSession`. The existing `resolveAccount` and the session code are refactored into `finishFacebookSignIn(request, deps, cookie, facebookId, via)` used by both flows, so the invite rules exist exactly once. Its account lookup is **scoped to the binding space**: it matches `facebookId = sub AND facebookIdVia = via`, with a null `facebookIdVia` counting as `own`. An id from the broker's Meta app and an id from the club's own app are different id spaces that can share digits, so a row bound under `own` is never matched by a broker `sub` and the reverse. Only a row whose role is `selector` can be signed in or bound; a row of any other role that somehow carries a `facebookId` gets the generic `not-linked` result and no session. No account is ever created from Facebook; the broker `name` is never stored or shown.
- **Binding record.** `users.facebookIdVia` (`own` | `broker`, hidden, set together with `facebookId` through the same `facebookBind` context; cleared whenever `facebookId` is cleared). The migration backfills `own` for every row that already has a `facebookId`, replaces the single-column unique index on `facebook_id` with a composite unique index on `(facebook_id, facebook_id_via)` (two people may legitimately hold the same digits in different id spaces; rows without a link have both null and never conflict), and code still treats a null via as `own`. The direct data-deletion and deauthorize callbacks only unlink rows with `via = own` (or null); the events endpoint only unlinks rows with `via = broker`.
- **Events** `POST /api/websport-auth/events` (404 unless effective mode is `broker`): body at most 8 KB, `application/json`, shape `{ event: string }`. Verify the JWT exactly as in 3.3 (signature, `iss`, `aud`, `exp`/`iat`, `type` allowlist, `sub` digits, `jti` shape; no `club` or `nonce` check, the protocol does not put them in events). **The signature is verified first**: with a cached JWKS that is a local Ed25519 check, and an unknown `kid` is already limited to one refetch per 30 seconds. `facebook.data_deletion` and `facebook.deauthorize` both unlink: `users` where `facebookId = sub` and `facebookIdVia = 'broker'` get `facebookId` and `facebookIdVia` set to null (the club stores only the id, so unlinking is the deletion). A valid event always answers 200 `{}` whether or not a row matched (no membership oracle). **Events do not use the `jti` table**: unlinking is idempotent, and brokers retry after timeouts, so a redelivered event simply unlinks nothing and answers 200 `{}` again; a replay never answers 400. Anything that fails verification answers 400 `{ "error": "invalid event" }` with no detail. **Flood control counts only failures**: a request that fails verification takes one slot of the `broker-events:bad` ceiling (120 per hour, `hit`; plus the soft per-IP bucket when a trusted IP exists), and once that ceiling is spent further failing requests answer 429 without logging. A request with a valid signature never touches the limiter, so an anonymous caller cannot use up a shared allowance and cause a real `facebook.data_deletion` to be refused. The endpoint writes nothing for unauthenticated callers, so there is no table to grow.
- **Password fallback.** Password sign-in never depends on the broker. A broker outage shows the existing "Facebook sign-in did not work. Try again, or sign in with your password." (`e=failed`). A cached JWKS keeps verification working through a short outage; on a failed refresh a stale cache is used for at most one hour, then verification fails closed.
- **Trust model (stated in the docs and on the Sign-in settings help text).** In `broker` mode the club trusts the shared broker to say which Facebook person is signing in. A compromised or malicious broker could therefore sign in as any selector who has linked Facebook under the broker. The blast radius is deliberately small: only rows with the `selector` role can be signed in this way (never an editor or an admin), only rows that were bound through an invite (nothing is created or bound from Facebook alone), and a selector session reaches only the selector area. Staff accounts stay password only and are unaffected by the broker. Clubs that do not accept this trust choose `own-app` or `off`.

### 3.3 Verification module

`lib/signin/broker.ts` (pure where possible, `fetch` injected):
- `brokerConfig(env)`: `AUTH_BROKER_ORIGIN` must parse as an origin (https; `http://localhost` and `http://127.0.0.1` only when `NODE_ENV` is not production), no path, query, fragment or credentials, trailing slash trimmed; `AUTH_BROKER_CLUB_ID` must match `^[a-z0-9-]{1,64}$`. Anything else returns null (feature off), with a reason for the admin page.
- `getJwks(cfg, fetchImpl, now)`: cached per origin in module scope for 5 minutes; an unknown `kid` forces one refetch, at most once per 30 seconds; fetch has a 5 s timeout, `redirect: 'error'`, a 16 KB body cap and a JSON shape check; only `kty: OKP`, `crv: Ed25519`, `alg` absent or `EdDSA` keys with a string `kid` are kept.
- `verifyBrokerJwt(token, { cfg, ownOrigin, kind: 'assertion' | 'event', expect, now, fetch })`: token at most 4000 characters; `jwtVerify(token, createLocalJWKSet(jwks), { issuer: cfg.origin, audience: ownOrigin, algorithms: ['EdDSA'], clockTolerance: 5, currentDate })` (this rejects `none` and every HMAC or RSA algorithm, so the alg-confusion attack with the public key as an HMAC secret fails); then explicit checks: `iat` not more than 5 s in the future; `exp - iat` at most 120 (assertion) or 600 (event), which rejects a misconfigured long-lived token; `sub` matches `^\d{1,40}$`; `jti` is a string of 16 to 64 URL-safe characters (shape only; consumption is the caller's job and happens for assertions only). Assertion only: `club === cfg.clubId`, `amr` includes `facebook`, `nonce` equals the cookie nonce by `timingSafeEqual`. Event only: `type` in the allowlist. `ownOrigin` is `payload.config.serverURL` (never the `Host` header).
- `consumeJti(payload, jti, expSeconds)` as in 3.2, called by the broker callback only.
- `testConnection(cfg, ownOrigin, fetchImpl)`: three read-only calls to the configured broker origin only (never a user-supplied URL): `GET /healthz` (expects `ok: true`, reports `facebookConfigured`, `keys`), `GET /.well-known/jwks.json` (at least one usable key), and a registration probe `GET /v1/facebook/start?club=&return_to=&nonce=&state=` with `redirect: 'manual'` using fresh random values: 302 means the club and return URL are registered and Facebook is configured at the broker (the redirect is not followed, so Facebook is never contacted), 400 means "this club or return URL is not in the broker's CLUBS", 503 means "the broker has no Facebook app yet". Each call has its own timeout and a plain-English result; the response is stored on `site-settings.signIn.lastTest` (never headers, bodies or env values).

### 3.4 Sign-in status inside Site settings (admin only, no new menu entry)

- The UI is the `signIn` group of the existing `site-settings` global (nav entry `site-settings` already exists and is admin only; `hiddenFromEditors` on the global and field-level `isAdmin` on the group). The status block, registration block, URL list and Test connection button are custom UI field components inside the group (the same pattern as `ThemeContrast.tsx` and `PlayerSyncPanel.tsx`), not a separate view and not a separate global. ## 4. WP-2: club fantasy cricket MVP (#36)

### 4.1 Scope

**In the MVP.** One competition per season. Members join with one shared link and choose their own team name and PIN (no accounts, no email). Each manager picks a squad of N **senior** club players (default 11) within a salary cap (default 100.0 credits) using prices set from past seasons by a deterministic formula that an admin can adjust (prices need no action by default). Prices are a percentile rank of points per game; they are not a rating of how good a player is, and the picker says so. One captain scores double. Squads can change until a round's lock, which is the first game start of that round; changes between rounds are limited by a transfer cap. Points come from the match store with a configurable scoring table. A stat that is null scores nothing and is never invented. Round and season leaderboards; the public view of the leaderboard is a committee toggle (default off), like best-player votes.

**Deferred and documented (issue #36 stays open for these).** Draft format (snake or auction, with turn order, timers and ownership rules); vice-captain and automatic substitutions; chips such as wildcard or triple captain; head-to-head leagues and mini-leagues; manager email or accounts and notifications; prizes, entry fees or any payment (the game is free to play, and the documentation says so; nothing here is a betting product); economy-rate and strike-rate bonuses (they need ball counts that are often null); viewing another manager's squad after lock; rescoring history on a scoring-table change after the season has opened.

**Definitions.** A *round* is one club weekend (Monday to Sunday, keyed by the Saturday, `groupByWeekend`). Rounds are **derived** from `selection-fixtures`; they are not a collection. A small table `fantasy-round-state` keeps only what cannot be derived: the stored `locksAt`, an admin `lockOverride`, and a manual-scored flag. A round's *lock* is the earliest `startsAt` of its non-removed `selection-fixtures` (falling back to the earliest `matches.startsAt`, then to 00:00 club time on the Saturday). **Locks only ever move earlier**: the stored `locksAt` is lowered whenever the nightly sync or a save sees an earlier start, and never raised (a fixture moved later does not reopen a round); the admin override can only move it earlier once any manager has a squad. A fixture counts as *terminal* when it has a stored FINAL match **or** its status is one with no result (washed out, abandoned, forfeited, cancelled, postponed; the exact status values are a constant in `lib/fantasy/rounds.ts`, taken in the first WP-2 commit from the statuses actually present in `selection-fixtures` and the match store, and pinned by a test). A round is *scored* when every non-removed fixture is terminal (a no-result fixture contributes 0 appearances), or when an admin used **Mark round scored** with a reason (stored on the round-state row, shown on the leaderboard as "closed by the committee"); until then its points are marked provisional. Prices are stored as **tenths of a credit** (integers) so there is no floating point money-like arithmetic.

### 4.2 Data model and migration

Migration `fantasy` (schema-qualified). Everything is an `internalCollection` (hidden, no REST write, written by code through the Local API after server-side checks). **No new global.** Five new tables (down from seven new objects): `fantasy-seasons`, `fantasy-round-state`, `fantasy-prices`, `fantasy-entries`, `fantasy-squads`. Together with `auth-broker-jtis` that is six tables for the wave.

- Switches that already have a home: a `fantasy` group on the existing `site-settings` global (`read: anyone` for the public site, so each field has its own access). `enabled` (default false; field read `anyone` because public pages must know, update `isAdmin`), `publicLeaderboard` (default false; read `anyone`, update `isStaff`), `linkVersion` (default 1; **read and update `isAdmin` only**, because the join token is derived from it; rotating it kills the link, every remembered device and every lock key, as for availability) and `competitionName` (default "Fantasy cricket", read `anyone`, update `isStaff`). The editable **rules live on the season** (below), not in a second place: nothing is "defaults for the next season".
- `fantasy-seasons`: `seasonStartYear` (unique), `name`, `status` (`draft | open | closed`), and the **editable rules**: `maxEntries` (300), `squadSize` (11), `salaryCapTenths` (1000), `captainMultiplier` (2), `transfersPerRound` (3, 0 means unlimited), `minPriceTenths` (40), `maxPriceTenths` (140), `priceSeasonsBack` (2), `priorGames` (3), `minGamesForPrice` (3), `blockedWords`, and `scoring` (table below). Rules are edited in the `/fantasy` view on a `draft` season (creating a draft copies the previous season's rules, or the built-in defaults for the first). Opening the season freezes them: a rule field is read-only once `open`, so a mid-season edit never silently reorders the table (the explicit answer to "rescoring history", deferred). `blockedWords` stays editable at any time because it protects names, not scores.
- `fantasy-round-state` (overrides only): `season`, `weekendKey` (Saturday date), `locksAt` (date, the lowest start seen, never raised), `lockOverride` (date, optional), `scoredManually` (checkbox), `scoredReason` (text, required when set), `scoredBy` (user), `scoredAt` (date). Unique on `(season, weekendKey)`. The row is created lazily by the sync or on first save; label, status (`upcoming | locked | scored`), fixtures and points are all computed from `selection-fixtures` and the match store.
- `fantasy-prices`: `season`, `player`, `priceTenths`, `autoPriceTenths`, `overridden` (checkbox), `available` (checkbox, false removes the player from the pool), `basis` JSON (appearances, points, shrunk points per game, rank). Unique on `(season, player)`. Rows are created for senior, visible players only.
- `fantasy-entries` (managers): `season`, `teamName`, `nameKey` (normalised, unique per season, so names cannot be impersonated by case or spacing), `pinHash`, `pinSalt` (field access `nobodyField` for read and write), `pinSetAt`, `mustChangePin` (set by a committee reset), `deviceCodeHash`, `deviceCodeExpires` (one-time add-a-device code, `nobodyField`), `disabled`. No email, phone or real name is stored. REST read: admin only, and never the hash fields.
- `fantasy-squads`: `entry`, `round` (the `weekendKey`), `captain` (relationship to players), `spentTenths`, `transfersUsed`, `picks` (array of `{ player }`), `savedAt`. Unique on `(entry, round)`. **No REST read for any role** (`read: nobody`, like the writes): an editor who also plays must not be able to browse rivals' picks before the lock, so squads are only read by server code that states the lock condition (a squad is readable by the leaderboard and the admin view only when its round's lock has passed) and by the owning manager through the cookie. The committee sees **counts only** before the lock (managers who have saved a squad for the open round, managers who have not).

Scoring table defaults (all editable on the draft season, `fantasy-seasons.scoring`, whole numbers, negatives allowed for a duck): appearance 2; run 1; four bonus 1 (counted only when `fours` is not null); six bonus 2 (only when `sixes` is not null); fifty bonus 8; hundred bonus 16 (cumulative on top of the fifty bonus); duck -3 (only for a batter who was out for 0, `status = 'out'` and not retired); wicket 20; maiden 6; three-wicket bonus 6; five-wicket bonus 12 (cumulative); catch 8; stumping 12 (only when `stumpings` is not null); run-out 10 (only when `runOuts` is not null). Keeper catches count with catches only if the `deriveFacts` credit rules do not already include them (checked in the first WP-2 commit by reading `lib/stats/match/facts.ts` and its tests, then pinned by a unit test). A pick whose player is no longer in the game scores 0 (see 4.5).

### 4.3 Pricing formula (deterministic, admin-adjustable)

`lib/fantasy/pricing.ts`, pure. For every eligible player: `G` = appearances and `P` = total fantasy points over the `priceSeasonsBack` most recent stored seasons, scored with the season's scoring table over `getAllFacts`/`getSeasonFacts`. Let `mu` be the mean points per appearance across eligible players with `G > 0`. Shrunk rate `s = (P + priorGames * mu) / (G + priorGames)`; a player with `G < minGamesForPrice` is priced on `s` as computed (so a debutant sits near the middle **by design**, never at an extreme) and a player with no data at all gets `s = mu`. Percentile rank `r` of `s` among eligible players (ties broken by player id, so the same inputs always give the same output). `price = min + (max - min) * r`, rounded to the nearest 5 tenths and clamped to `[min, max]`. The inputs (`G`, `P`, `s`, `r`) are stored in `basis` so the admin sees why. **Prices need no action by default**: they are computed by one guided step when the season is set up (see 4.7), and while the season is `draft` an admin can recalculate. After the season opens, overrides and the `available` flag stay editable, and **"Add missing players"** creates default-priced rows (the same formula, so a debutant sits near the middle) for eligible players who have no `fantasy-prices` row, for example a mid-season signing; it never creates a row twice and never touches an existing price. Changing a price after the season opens never invalidates a saved squad; the new price applies from the next time that manager saves. **Honesty in the picker**: a price is a percentile rank of points per game, not a statement about quality, and the picker shows the games count next to points per game, flags any price based on fewer than `minGamesForPrice` games ("based on n games, priced near the middle"), and carries one line of help text saying debutants and thin data sit near the middle by design.

**Eligible players** (`lib/fantasy/eligibility.ts`): `isHidden = false` **and `isJunior = false`** (the `players.isJunior` "under 18" flag, tested explicitly, not "the stats senior filter"), in a current squad or with an appearance in the last `priceSeasonsBack` seasons, and `available`. Minors are never priced, rated, ranked, listed in the picker or scored: pricing, the picker, the facts-to-points map and the leaderboard drop them by the flag, and `mu` and the percentile ranks are computed without them. A unit test pins it (a junior with many appearances gets no price, is not in the pool and does not move anyone else's rank), and the eligibility is the single function every consumer uses. The role shown in the picker comes from the existing effective role (`lib/selection/roles.ts`) where a profile exists, otherwise "Player" (no role is invented).

### 4.4 Join, identification and throttling (reuse of the availability pattern)

- Link: `/fantasy/play/<token>` where `token = base64url(HMAC(hkdf('fantasy-link'), 'v' + linkVersion))` (new HKDF label `fantasyLink`; `tests/secrets.test.ts` already requires distinct labels, so it is extended). `resolveFantasyLink` returns the settings or `null`; a wrong token, a rotated link, a disabled competition and a season that is not `open` all render the same plain 404.
- Join form: team name (2 to 30 characters; letters, digits, spaces and basic punctuation; trimmed and collapsed; rendered escaped) and a **6 digit PIN** chosen by the manager, entered twice. The PIN must not be on the banned list (all one digit, ascending or descending runs, `123123`-style repeats, and common patterns); the form says "choose a PIN that is hard to guess". The join page warns, above the name field: **"Do not use a surname or a child's name. The team name can appear on the leaderboard."** Names are checked against the `blockedWords` setting. **A taken name and a blocked name give the identical message** ("That name is not available. Try another.") with the same status and the same timing path, so neither the blocklist nor the existing names can be probed. Returning: team name plus PIN. Both are one form (`mode=join|return`) handled by a server action.
- PIN storage: `hashPin` from `lib/selection/pin.ts` (scrypt with the HKDF pepper). Identification: `lib/fantasy/identify.ts` mirrors `identify()`: IP bucket `fantasy` (new `IpBucket`, soft rule, skipped when there is no trusted IP), per-entry counter (`fantasy:link:<v>:entry:<id>`, five failures then a 15 minute lock doubling to one hour), per-name bucket for unknown names (fixed bucket count with the server-keyed hash from `nameBucket`, so random names do not grow the table and a name cannot be probed), a **whole-link ceiling of 60 failed attempts per hour** (`fantasy:link:<v>:all`; not the 300 per hour copied from availability), the throttle slot taken **before** the PIN is checked, a dummy scrypt for unknown names so known and unknown cost the same, one generic failure message, one generic lock message. Registration is throttled by the same IP bucket plus `maxEntries`.
- **Stakes, stated honestly.** With 6 digits there are about 10^6 PINs. The per-entry lock allows roughly 120 guesses a day against one team (a 0.012 percent chance a day), and the whole-link ceiling allows at most about 1,440 guesses a day across all teams (about 0.14 percent a day that any team is taken over by guessing). A 4 digit PIN would have been guessable in weeks by anyone holding the link. What is at risk is a fantasy team: no money, no personal data beyond the team name. The documentation says this, and says the whole-link ceiling also means a determined person can briefly stop new-device sign-ins by spending it (remembered devices are never throttled, and the committee can rotate the link). Self-service recovery paths below keep the load on the committee small.
- Remembered device: signed cookie `${COOKIE_PREFIX}_fantasy` (`__Host-` in production, HttpOnly, SameSite=Lax, 90 days) holding only `{ entryId, linkVersion, iat }` (HKDF label `fantasyCookie`). It is invalid when `linkVersion` changed, when the entry is disabled or gone, or when `pinSetAt` is later than `iat` (a PIN change or reset ends old devices, except the device that just changed it, which is re-issued a cookie). A remembered device is never throttled, exactly like availability.
- **Forgotten PIN and new phones (self-service first).** (a) *Change PIN*: a signed-in device can change the PIN after re-entering the current one (counted against the per-entry throttle). (b) *Add this device*: a signed-in device generates a one-time 6 digit code (also shown as a QR of the join link that pre-fills the form) valid for 10 minutes and single use, stored only as a hash; a new device enters team name plus code and is signed in without the PIN, through the same throttle as PIN attempts (so the code is no easier to brute force than a PIN). Generating a new code voids the old one. (c) *Committee reset* is the last resort: the admin view has a **manager picker with search by team name** (shows team name and join date only, never a PIN or hash) and a Reset PIN action that sets a temporary PIN and `mustChangePin`. The temporary PIN is shown **once, only to the person who pressed the button**, in the action response; it is never stored in plain text, never logged, never written to a notification or the audit line, and not retrievable afterwards. The manager must replace it on first sign-in. Every reset and every disable adds a plain line to the admin notification centre (admin-only lines, wording in `payload/admin/copy.ts`): "PIN reset for <team name> by <actor>, <date>." and "<team name> was disabled by <actor>, <date>.", so a reset by an editor who also plays is visible to the admin. Self-service email or phone recovery is deferred (it would need contact data this MVP deliberately does not store).
- Privacy: the join page states what is stored (team name and a hashed PIN), who can see it (the committee; the team name appears on the leaderboard only when the committee makes it public) and how to be removed (ask the committee; admin "Remove manager" deletes the entry and its squads).

### 4.5 Squad rules (server-side, in `lib/fantasy/squad.ts`, pure and unit tested)

On every save, all checks run again on the server regardless of what the browser sent: the round is the next round whose lock is in the future (a save for any other round is refused); **the lock used is `min(stored locksAt, earliest startsAt of the round's non-removed fixtures at save time)`**, computed from the current `selection-fixtures` (so a start time that moved earlier since the last nightly sync still locks the round, and the lowered value is written back); the lock is never raised; `now < lock` with the clock injected for tests; exactly `squadSize` distinct players, all eligible (not hidden, not junior, `available`); total of current prices at most the cap; a captain who is in the squad and in the game; transfers used (players in this round's squad that were not in the manager's previous squad, **not counting a replacement of a player who is no longer in the game**) at most `transfersPerRound` unless unlimited; the first squad has no transfer limit. **Players who become unavailable or hidden (or flagged junior) after being picked**: the pick is kept and shown as "no longer in the game", scores 0 (the facts layer excludes them, and the scorer maps a missing player to 0 on purpose), and the squad is then invalid for saving until the manager replaces them; the manager sees a banner "Replace <name> before the lock" on the team page. The replacement swap is not a transfer and does not use the transfer cap, but the cap and every other rule still apply to the new squad. If the manager does nothing, the carried-forward squad is scored with 0 for that pick (a captain who is no longer in the game scores 0 for the captain slot; there is no automatic substitute, which is deferred). A later round's squad is created by copying the previous round's squad when the manager has not saved (so doing nothing keeps the team). A locked or scored round's squad is never updated by any path (checked in the action and again by a `beforeChange` hook that refuses a write after the lock unless `context.fantasyRescore` is set by the sync code). Concurrent saves are safe because a squad is one row per `(entry, round)` written in a single transaction, and the last valid save before the lock wins.

### 4.6 Scoring and leaderboards

- `lib/fantasy/score.ts`: `scorePlayerGame(facts, table)` returns `{ points, parts }` where `parts` lists each rule that fired (used for the "why" breakdown). A missing fact means no part, never zero-filled data: `fours: null` fires no four bonus, `keeperCatches: null` adds nothing, an absent appearance scores 0 and shows "did not play". A player who played two games in a round (two teams) sums both.
- `lib/fantasy/queries.ts` (the only data layer the pages use, each query states its filter): `getRoundPoints(season, round)` builds a per-player points map from the cached public `FactSet` (`getSeasonFacts`) restricted to matches whose `localDate` falls in the weekend, so hidden players are excluded by the facts layer, and then drops any player who fails the eligibility flags in 4.3 (junior); `getLeaderboard(season, { round?, includeNames })` sums, per entry, each round's points of that round's squad, with the captain's points multiplied by `captainMultiplier`; tie-break: higher best single round, then earlier join. Results are cached with `unstable_cache` and a `FANTASY_TAG`, invalidated when the admin changes rules, prices, round state or entries and by the nightly sync (the same place `refreshSelectionFixtures` runs, followed by `syncFantasyRounds(payload)`, which lowers locks, creates round-state rows lazily and never unlocks a locked round). **A round is scored by the rule in section 4.1** (every non-removed fixture terminal, where a washed-out, abandoned, forfeited, cancelled or postponed fixture counts as scored with 0 appearances, or manually marked); a unit test with an abandoned fixture pins that the round becomes scored.
- Visibility of leaderboards: when `publicLeaderboard` is on, `/fantasy/leaderboard` shows team name, round points and total to anyone. When off, only an identified manager (valid cookie) and staff see it; everyone else sees "The leaderboard is shared with members who have joined." Neither state ever exposes PIN data, other managers' squads before the lock, or the join token.

### 4.11 Risks and external decisions

- Scoring weights and the price range are product choices; the defaults above are safe starting points and are shown to the committee before the season opens (the draft state exists for exactly this).
- Thin data: clubs with few stored games get coarse prices; shrinkage keeps debutants near the middle and the admin can override. The picker shows the games count and flags prices based on fewer than the minimum games.
- Scorecards can be amended after a game is first stored; rounds recompute from the facts layer on the next sync, so a leaderboard can move slightly. This is stated on the page.
- Fantasy is a free game; any prize, fee or betting-style use is outside this design and needs a legal check by the club (documented in the feature doc, not built).
- No credentials or external services are involved. PlayHQ is only reached by the existing nightly sync.

## 5. WP-3: multi-club template (#37)

### 5.1 Decisions

- **Deployment model: one deployment per club from this repository, single tenant, shared sign-in broker.** Each club gets its own copy of the repo (a fork or a "use as template" copy that keeps an `upstream` remote), its own Vercel project, Postgres database, Blob store, domain, cron and email sender. Why not multi-tenant: club data (members, fees, PINs, selections) is personal and financial, so one database per club is the simplest correct isolation; PlayHQ organisation, API credentials, cookie prefix, locale, timezone and season calendar are all per club; a Payload multi-tenant plugin would touch access control in every collection and make a single bug a cross-club leak; and clubs pay nothing extra for a separate free-tier project. The only shared service is the sign-in broker (WP-1), which holds one Meta app so no club needs its own. This is a recommendation for the owner to confirm; nothing else in this wave depends on a different answer.
- **No code edits for a new club.** Everything club specific is either env (documented, validated) or data (a club profile file loaded by the bootstrap script, then edited in the admin). The club's repo contains `clubs/<slug>/` (profile and assets) and nothing else that differs from upstream, so pulling upstream is a plain merge.
- **YAML is not supported.** JSON only (`clubs/<slug>/profile.json`), so the script needs no new dependency; the docs include a commented example using a `_comment` key that the validator ignores.

### 5.4 `bootstrap-club` script

`pnpm bootstrap:club --profile clubs/example-fc/profile.json --target <host>/<db> [--confirm] [--force] [--skip-admin] [--skip-assets]` (`payload run payload/scripts/bootstrap-club.ts --`). Guarded like every operator script: it calls `checkGuard` from `payload/scripts/_guard.ts` (`--target` must equal `DATABASE_URI`; `ALLOW_REMOTE_DB=yes` for a remote host; the 5 second pause unless local with `GUARD_NO_DELAY=1`). **Dry-run is the default**: without `--confirm` it validates everything, connects read-only, and prints the plan (migrations pending, globals that would be created or left alone, **a per-field diff for every global that already has a saved row (saved value, profile value, and whether the field would be filled, kept or skipped)**, the admin that would be created, assets that would be uploaded, env lines the operator still has to set) and writes nothing. With `--confirm`:
1. Preflight: profile valid; required env present and consistent (`CANONICAL_HOST` host equals `club.siteUrl` host, `COOKIE_PREFIX` set and not `llcc` unless the profile says it is Lang Lang, `PLAYHQ_ORG_ID`/`PLAYHQ_TEAM_PREFIX` match the profile, `PLAYHQ_CLIENT_ID` may be empty); refuses a target that already has a saved `club` global or any user unless `--force`. **`--force` has one meaning: it fills only empty fields and never overwrites a saved non-empty value** (so a club that has customised `club.name` keeps it), never deletes data or users and never resets an existing admin. A re-run without `--force` changes nothing and says why (this is the same rule as 5.6 test 3). Fields the profile does not supply are left as they are.
2. Migrate a blank database (`payload.db.migrate()`); in dry-run only the pending count is read.
3. Seed `club` from `buildClubDefaults(profileIdentity, profile.copy)` through the existing `seedClubGlobal` path, `theme` (palette, derived shades, heading font), `social-settings`, `office-settings`, `site-settings` and a default `sign-in-settings` row.
4. Create the first admin with `context.seedAdmin` (same mechanism as `seed:admin`), skipped if the email exists.
5. Upload assets into `media` (local `./media` when no Blob token, which the safety guard enforces locally). A remote run that uses the Blob plugin needs `BLOB_READ_WRITE_TOKEN` and, because `assertSafeEnv` refuses a Blob token off Vercel, `ALLOW_REMOTE_BLOB=yes`; **without it the script skips assets and prints "Assets skipped: upload them in the admin (Media library), then set the logo, favicon and share image under Club details"**. `--skip-assets` does the same on purpose.
6. Print the next steps: the env lines to set on the host, the broker `CLUBS` entry for this site, the cron note, DNS, and `pnpm seed:demo` is **not** suggested for production. It also writes `clubs/<slug>/env-checklist.md` (see 5.5): every variable name with where it is read, whether it is required, and its status in the current environment as set, missing or invalid (names only, never values), so a non-developer can see what is left to do.
The orchestration lives in `payload/bootstrap/run-bootstrap.ts` (`runBootstrap(payload, profile, opts)` returning a structured report) so the integration test and the script share it; the script file is only argument parsing and the guard. It makes no network call (no PlayHQ, no broker, no email).

### 5.8 Risks and external decisions

- Splitting `club-defaults.ts` is the largest refactor in the wave; the unit tests that pin the Lang Lang text (moved to the preset) are the safety net, and production Lang Lang is unaffected because its `club` row is fully saved and `assertClubPreset` fails the build or startup if `CLUB_PRESET` is missing on the Lang Lang host. ## Appendix: considered and not adopted

- Using `createRemoteJWKSet` directly: not adopted because it cannot take an injected `fetch`, so tests would need a network or a global patch; a 40 line cache with `createLocalJWKSet` gives the same verification and testable fetch.
- Fantasy accounts through selector Facebook sign-in: not adopted; members are not selectors and the issue asks for link plus PIN with no accounts.
- Reusing `player-selection-profiles` PINs for fantasy: not adopted; it would exclude non-players and tie fantasy PINs to the availability PIN lifecycle.
- A single "Settings" mega-page for sign-in plus selectors: not adopted; sign-in mode is admin only while Selectors is `forEditors`.
- Multi-tenant runtime (a `tenant` column everywhere): not adopted for the reasons in 5.1.
- YAML profiles: deferred; JSON needs no dependency.

## Appendix: review findings adopted with changes or declined in part

The 29 review findings were all valid in substance and are resolved above. Where the proposed fix was not taken as written:

- **#1 events limiter.** Both proposed fixes were combined: the signature is checked first and only failures are counted. No valid event can be refused by the limiter; the failure ceiling only bounds noise.
- **#4 default mode.** Resolved by making the stored `broker` mode resolve to `own-app` when only the own-app env is set, plus a cutover-checklist line, not by changing the default.
- **#6 PIN.** Six digits were chosen over 4 to 6 digits with a banned list; a banned list still applies to the 6 digit space. The residual risk is stated in the docs rather than eliminated.
- **#7 pre-lock squads.** Taken further than proposed: `fantasy-squads` has no REST read at all for any role, not only before the lock; server code serves post-lock squads. Resetting a PIN stays allowed for editors (the committee needs it) but is audited and the temporary PIN is shown only to the actor.
- **#16 sign-in settings.** Folded into `site-settings` as proposed, so the question of why a separate admin-only page would be acceptable does not arise. The earlier "mega-page" rejection (sign-in plus Selectors on one page) stands for editor-visible pages.
- **#17 prices.** "Recalculate" is no longer a standing control; it is part of the guided season setup, with Add missing players for later signings.
- **#22 preset guard.** Enforced on the Lang Lang host only. A Lang Lang preview on another host cannot be detected from the host, so the control there is the checklist and the preview env var; this is stated as residual risk.
- **#28 rounds.** `fantasy-rounds` is replaced by a small `fantasy-round-state` table, not removed entirely: the lowest-seen lock must be stored to guarantee that a lock is never raised (#11), so that single column cannot be derived.
- **#29 names.** "Fantasy cricket" and "credits" stay as neutral defaults; the env list is handled by one checked manifest rather than by shortening it.
